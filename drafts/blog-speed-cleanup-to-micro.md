언제부턴가 내 블로그가 느렸다.
글 목록을 열면 썸네일이 한 장씩 천천히 그려졌고,
글 상세는 상단 배너가 뜰 때까지 한참 걸렸다.

이미지가 느리니 자연스럽게 이미지를 담고 있는 S3를 의심했다.
"S3 저장소가 특히 느린 거 아닐까?"

그래서 Claude Code를 붙잡고 하나씩 재보기 시작했다.
결론부터 말하면 S3는 아무 잘못이 없었다.
그리고 그 하루의 끝에는 EC2를 t4g.small에서 t4g.micro로 내리고 있었다.


## S3는 0.1초 만에 답하고 있었다
먼저 S3에 직접 요청을 보내 봤다.
연결에 0.01초, 첫 바이트까지 0.1초 남짓.
서울 리전의 S3는 멀쩡히 빠르게 답하고 있었다.

그런데 이상한 숫자가 하나 보였다.
썸네일 원본이 장당 **1.5MB짜리 PNG**였다.

블로그 썸네일은 Next.js의 `<Image>` 컴포넌트를 거친다.
원래대로라면 `/_next/image?url=...&w=640`으로 요청했을 때
서버가 640px로 줄이고 webp로 바꿔서 수십 KB짜리를 내려줘야 한다.
정말 그러고 있는지, 폭을 바꿔 가며 요청해 봤다.
| 요청한 폭 | 받은 크기 | 형식 |
|---|---|---|
| w=640 | 1,529,789 바이트 | PNG |
| w=1080 | 1,529,789 바이트 | PNG |
| w=3840 | 1,529,789 바이트 | PNG |
폭이 뭐든 바이트 수가 한 자리도 다르지 않았다.
**최적화가 아예 안 되고 원본이 그대로 나가고 있었던 것이다.**


## 범인은 조용히 꺼져 있던 sharp
Next.js는 이미지를 줄일 때 `sharp`라는 라이브러리를 쓴다.
그런데 `output: "standalone"`으로 빌드하면,
이게 의존성에 없을 때 최적화를 포기하고 원본을 그대로 돌려준다.

무서운 건 이게 에러가 아니라는 점이다.
응답은 200으로 멀쩡히 나가고, 로그에도 눈에 띄는 경고가 없다.
몇 달 동안 아무도, 그러니까 내가 몰랐던 이유다.

고치는 건 이 한 줄이었다.

```bash
npm install sharp
```

배포하고 나니 같은 썸네일이 이렇게 바뀌었다.
| | 이전 | 이후 |
|---|---|---|
| 썸네일 (w=640) | 1.5MB PNG | 21KB webp |
| 한 장 받는 시간 | 3~20초 | 0.7초 |
| 캐시 | 60초, Cloudflare 캐시 안 됨 | 1년, Cloudflare 엣지 캐시 |
캐시도 같이 손봤다.
S3 키에 업로드 시각이 들어가서 같은 주소의 이미지는 바뀔 일이 없다.
그래서 `minimumCacheTTL`을 1년으로 늘렸다.

그리고 `/_next/image`는 확장자가 없어서 Cloudflare가 기본으로는 캐시하지 않는다.
Cache Rule을 하나 따로 만들어 줬다.
이제 두 번째 요청부터는 서버까지 오지도 않는다.

판별법 하나는 기억해 둘 만하다.
**폭을 바꿔 요청했는데 `content-length`가 같으면, 최적화가 꺼져 있는 것이다.**


## 서버는 서울인데 왜 LA를 찍고 오지
이미지를 고쳤는데도 체감이 시원하지 않았다.
그래서 이번엔 Cloudflare를 건너뛰고 EC2에 직접 요청을 보내 비교해 봤다.
| 요청 | EC2 직접 (서울) | Cloudflare 경유 |
|---|---|---|
| 글 목록 HTML | 0.14~0.40초 | 0.85~6.5초 |
| JS 파일 13KB | 0.045초 | 0.6~9.1초 |
서버는 빠르게 답하고 있었다.
느린 건 그 앞 구간이었다.

Cloudflare가 붙여주는 `cf-ray` 헤더 끝에는 요청을 받은 거점의 공항 코드가 붙는다.
우리 집 회선(KT)에서는 그게 **`LAX`**로 찍혔다.

서울에 있는 내가 로스앤젤레스 거점으로 갔다가,
다시 서울의 EC2로 오고, 또 LA를 거쳐 돌아오고 있었던 것이다.
태평양을 두 번 왕복하는 셈이다.

같은 회선에서 Cloudflare 자체 사이트는 서울(`ICN`)로 붙는다.
그러니 무료 플랜에 배정되는 경로 문제로 보인다.

이건 아직 해결하지 못했다.
회색 구름(DNS only)으로 바꾸면 빨라지지만 Cloudflare의 보호 기능을 전부 잃는다.
유료 플랜은 서울 거점이 보장되는지 확실하지 않다.

그래서 일단 감사 로그에 방문자가 어느 거점을 거쳐 왔는지를 남기기 시작했다.
한국 방문자 중 얼마나 LA로 빠지는지 며칠 쌓아 보고 정하려 한다.


## 이미지 다이어트
범인을 잡고 나니 이미지 자체도 너무 무거웠다는 게 보였다.

S3에 이미 올라간 이미지는 주소를 바꾸면 글 본문을 전부 고쳐야 한다.
그래서 **같은 이름 그대로 덮어쓰는 방식**으로 줄였다.
PNG는 256색 팔레트로 압축했는데, 1:1로 확대해 비교해도 차이가 거의 없었다.

버킷에 버전 관리가 꺼져 있어서 로컬 백업이 유일한 원본이었다.
그래서 S3의 ETag가 백업과 같을 때만 덮어쓰게 했다.

GIF는 좀 애먹었다.
색을 128개로 줄이면 크기는 7분의 1이 되는데,
배경 픽셀을 찍어 보니 흰색이 회색으로, 남색이 보라빛으로 바뀌어 있었다.

흰 페이지 위에 회색 박스가 뜨는 꼴이라 포트폴리오 쪽 GIF는 손대지 않았다.
GIF는 결국 동영상으로 바꾸는 게 정답인 것 같다.

앞으로 올리는 이미지는 아예 올리기 전에 줄이도록 했다.
에디터에 파일을 넣으면 브라우저가 가로 2048px 이하로 줄이고 webp로 바꿔서 올린다.
같은 원본으로 비교하면 차이가 꽤 난다.
| 원본 | 기존 이미지 정리 (PNG 유지) | 새 업로드 (webp 변환) |
|---|---|---|
| AI 생성 이미지 2.7MB | 824KB | 267KB |
| 사진 2.2MB | 828KB | 112KB |
프론트 레포 안의 정적 파일도 가관이었다.
그룹별 기본 배너 7장이 3840px PNG로 장당 12MB, 합쳐서 87MB였다.
화면에는 700px 남짓으로 표시되는 이미지다.

1440px webp로 바꾸니 7장 합쳐 2MB가 됐다.
메인 배경의 백합 3D 모델도 삼각형이 54만 개였는데,
어차피 ASCII 문자로 바꿔 그리는 배경이라 13%만 남겨도 티가 안 났다.
| 항목 | 이전 | 이후 |
|---|---|---|
| S3 이미지 (30장) | 37.5MB | 10.7MB |
| 프론트 레포 정적 파일 | 198MB | 62MB |
| 프론트 Docker 이미지 | 482MB | 331MB |
정리하다가 버그도 하나 주웠다.
포트폴리오 이미지 폴더 이름이 `SEA-PEARL`인데 페이지는 `sea-pearl`로 요청하고 있었다.
맥은 대소문자를 구분하지 않아서 로컬에선 멀쩡했고,
리눅스인 서버에서만 조용히 404가 나고 있었다.

(삽화 자리)

## 백엔드가 메모리를 97% 쓰고 있었다
이미지를 정리하면서 서버 메모리를 보다가 더 큰 게 나왔다.
백엔드 컨테이너가 한도 384MB 중 **373MB**를 쓰며 스왑을 타고 있었다.
글이 80개 남짓인 블로그 API가 쓸 양이 아니다.

첫 번째 범인은 `geoip-lite`였다.
감사 로그에 "대략 어느 도시에서 접속했는지"를 남기려고 넣은 라이브러리다.
그런데 이 녀석은 불러오는 순간 IP 위치 DB 전체를 메모리에 올린다.

로컬에서 재보니 이거 하나가 **약 210MB**를 잡고 있었다.
쓰임새는 도시 이름 하나였는데.
Cloudflare가 무료로 붙여주는 위치 헤더(`cf-ipcity`)로 바꾸고 지워 버렸다.

두 번째는 Prometheus였다.
처음 블로그를 만들 때 모니터링을 공부해 보겠다고 Grafana와 함께 붙였었다.
메모리가 아까워서 수집 서버 컨테이너는 오래전에 내려둔 상태였다.

그런데 앱 쪽 코드는 그대로였다.
**아무도 읽어가지 않는 지표를 매 요청마다 메모리에 쌓고 있었던 것이다.**

게다가 라벨에 쿼리스트링까지 붙은 실제 URL을 넣고 있었다.
처음 보는 URL이 올 때마다 카운터가 새로 생기고, 지워지지 않는다.
실제로 쌓인 양은 몇 MB 수준이었지만,
누가 무작위 쿼리를 계속 보내면 끝없이 늘어나는 구조였다.

세 번째는 서버 자체였다.
EC2가 **1년 2주 동안 한 번도 재부팅되지 않았고**,
그동안 커널이 잡아두고 돌려주지 않는 메모리가 224MB까지 쌓여 있었다.
재부팅하니 50MB가 됐다.

서버를 들여다보다 더 놀란 것도 있다.
이 서버의 OS가 2025년 5월 이후로 보안 업데이트를 한 번도 받지 않았다.

Amazon Linux 2023은 설치 당시 릴리스 버전에 고정되어 있어서,
그냥 `dnf upgrade`를 하면 "받을 게 없다"고 나온다.
`--releasever=latest`를 붙여야 새 릴리스로 올라간다.

그걸 몰라서 1년 넘게 커널 패치 없이 돌고 있었다.
240개 패키지를 한 번에 올리고,
매월 첫째 일요일 새벽 4시에 알아서 업데이트하는 타이머를 걸어 뒀다.


## 그리고 서버를 죽였다
여기서 사고가 하나 있었다.

메모리 누수를 확인하려고,
한도에 꽉 차 있던 백엔드 컨테이너 안에서 진단용 node 프로세스를 하나 띄웠다.
정확히는 Claude가 띄웠다.

그 순간 컨테이너가 버티지 못했고, **백엔드 본체 프로세스가 죽었다.**

죽은 것까지는 괜찮다.
재시작 정책이 있으니 몇 초면 다시 뜬다.
문제는 코어 덤프였다.

운영체제는 죽은 프로세스의 메모리를 통째로 디스크에 떠 둔다.
스왑에 밀려나 있던 메모리를 다시 읽어 와서 압축하느라 이게 **4분 16초** 걸렸다.
그동안 컨테이너는 "실행 중"으로 보이는데 API는 응답하지 않았다.

코어 덤프 기록을 보니 9월에도 백엔드가 같은 식으로 세 번 죽은 적이 있었다.
그때 무슨 일이 있었는지는 알 수 없었다.
로그가 컨테이너 안에 있어서 재배포할 때 같이 사라졌기 때문이다.

그래서 몇 가지 장치를 넣었다.

먼저 Node 힙 상한(`--max-old-space-size`)을 컨테이너 한도보다 낮게 걸었다.
이게 없으면 V8이 한도를 모른 채 쓰다가 스왑에 빠져, 죽지도 못하고 멈춘다.
상한이 있으면 깔끔하게 죽고 몇 초 만에 다시 뜬다.

죽을 때 Node 진단 리포트도 남기게 했다.
여기서 하나 걸린 게 있는데, 기본 설정으로는 리포트에 **환경변수가 통째로 담긴다.**
DB 비밀번호와 JWT 키까지.
`--report-exclude-env`를 꼭 같이 줘야 한다.

로그와 리포트는 서버 디스크에 마운트해서 재배포해도 남게 했고,
코어 덤프는 "죽었다는 기록"만 남기도록 바꿨다.

한도에 붙어 있는 프로덕션 컨테이너 안에서 진단 명령을 돌리면 안 된다.
이건 몸으로 배웠다.


## 그래서 t4g.micro로
여기까지 정리하고 나니 숫자가 완전히 달라져 있었다.
| 항목 | 아침 | 저녁 |
|---|---|---|
| 백엔드 메모리 | 373MB (한도 97%) | 약 75~110MB |
| 커널 회수 불가 메모리 | 224MB | 50MB |
| 서버 전체 메모리 사용 | 약 830MB | 약 380MB |
| 스왑 사용 | 78MB | 0 |
이 정도면 메모리가 절반(1GB)인 t4g.micro로 내릴 수 있겠다 싶었다.

내리기 전에 컨테이너 한도를 256MB로 낮췄는데, 여기서 하나가 더 걸렸다.
배포할 때 도는 DB 마이그레이션이 **256MB를 꽉 채운 것이다.**

ts-node로 TypeScript 원본을 그 자리에서 컴파일하면서 돌리고 있었고,
그 바람에 컴파일러까지 메모리에 올라갔다.
Docker 이미지에 이미 빌드된 JavaScript가 있으니 그걸 node로 돌리게 바꿨다.
| 마이그레이션 실행 방식 | 최고 메모리 | 시간 |
|---|---|---|
| ts-node (원본 즉석 컴파일) | 256MB | 16초 |
| node (빌드된 JS) | 26MB | 1초 |
탄력적 IP가 붙어 있어서 인스턴스를 껐다 켜도 주소는 바뀌지 않았다.
콘솔에서 중지, 유형 변경, 시작. 그게 끝이었다.

컨테이너 다섯 개가 알아서 다시 떴고,
전환 직후 916MB 중 382MB를 쓰며 스왑은 쓰지 않았다.
| | t4g.small | t4g.micro |
|---|---|---|
| 메모리 | 2GB | 1GB |
| 월 비용 | $15.18 | $7.59 |


## 정리
돌아보면 처음 의심했던 S3는 끝까지 아무 잘못이 없었다.
범인은 매번 "있는 줄도 몰랐던 것"이었다.

에러 없이 원본을 내보내던 이미지 최적화,
도시 이름 하나 때문에 210MB를 잡고 있던 라이브러리,
수집 서버도 없는데 지표를 쌓던 코드,
1년 넘게 재부팅도 업데이트도 안 된 서버.
하나같이 조용해서 눈에 띄지 않았다.

"S3가 느린 것 같다"는 감으로 출발했다면
S3 앞에 CloudFront를 붙이는 엉뚱한 작업을 하고 있었을 것이다.
폭을 바꿔 요청해 보고, 서버에 직접 붙어 보고,
컨테이너의 메모리를 쪼개 보고 나서야 진짜 원인이 보였다.

이 과정에서 인증 코드도 통째로 다시 짰는데, 그건 길어서 다음 글로 뺀다.
