# 내 사이드 프로젝트 워크스페이스를 AI-Native로 만들었다 — 기억은 쌓는 것보다 안 쌓는 게 어렵다

## 새로 들어간 회사에서 가장 신박했던 일 방식

신규로 들어온 회사에선 전 직원이 AI를 쓰며 서로의 작업 맥락을 모두 하나의 저장소에 저장하고 있더라.

PM님도 PRD와 와이어프레임을 MD, HTML 파일들로 만들어 공유한다.
그런데 이걸 슬랙 같은 메신저로 보내는 것이 아니라,
**"OO님, PRD 문서 다 작성했으니 pull 받으시면 돼요~"**라고 말해준다.

이걸 가능하게 해주는 시스템은 camfit-playground라는 지식 저장소와
camfit-playground-framework(cpf)라고 불리는 전용 도구다.
사실 그 실체는 **하네스가 잘 갖춰진 에이전트 시스템과 전사 직원이 쌓은 md 파일**이다.
엄청나게 고차원적이어서 이해 못 할 시스템은 아니었다.

하지만 나는 30~40명이나 사용하는 하네스 엔지니어링된 AI 회사 맥락 공유 시스템을 만져본 적이 없어서,
신기해서 주말 동안 CPF를 디깅해봤다.

## 내 개인 프로젝트에 도입할 아이디어

그리고 떠오른 아이디어는,
**'내 개인 작업 워크스페이스도 이렇게 AI-Native Workspace로 만들어보자'**였다.
내 여러 개인 사이드 프로젝트들의 진행 맥락과 최근 아이디어,
기획적인 고민 지점들을 놓치지 않고 md 문서로 쌓는 것이다.

비서를 만드는 감각과도 비슷할 것이다.
'언제 OO앱을 개편하려 했는데 어떻게 하려고 했는지 기억이 안 나네. 네가 추적해줄 수 있어?'라고 물어보면
그때의 맥락을 파악해서 다 알려주는 게 가능해질 것이다.

![](https://bumang-blog-s3-storage.s3.ap-northeast-2.amazonaws.com/prod/thumbnails/1784994006520_image.png)

회사 워크스페이스의 구조를 모두 다 해체 분석하는 건 조금 양심에 찔리고,
내 개인 AI 하네스 시스템은 어떻게 구성했는지를 설명해보려고 한다.

그리고 이 글의 후반부는 그 시스템을 만들고 3주쯤 굴린 뒤에 부딪힌 진짜 문제에 대한 이야기다.
결론부터 말하면, md를 **쌓는** 건 하나도 안 어려웠고 **안 쌓는 게** 훨씬 어려웠다.

## 구조 — 매니저 레이어 하나와 독립 레포들

내 사이드 프로젝트들은 원래 `~/Work/private` 밑에 그냥 나란히 놓여 있었다.
여기에 한 층을 얹었다. 프로젝트들을 관장하는 **매니저 레이어**다.

```
bumang-workspace/      # 독립 git repo — 매니저 레이어만 추적
├── CLAUDE.md          # 매니저의 뇌 — 역할·프로토콜·스택 시그니처·포트
├── PROJECTS.md        # 포트폴리오 스냅샷 — 스택·상태·다음 할 일
├── memory/            # 비서의 장기기억
│   ├── preferences.md #   유저 성향 · 매니저 행동 규칙
│   └── decisions/     #   의사결정 로그
├── .claude/
│   ├── settings.json      # SessionStart 훅 등록
│   ├── session-brief.sh   # 세션 시작 브리핑 생성
│   ├── scripts/           # pull/push 유틸
│   └── skills/            # /pull-all · /commit-all · /commit-push · /push-repo
│
├── ant-index/          (독립 repo) 주식 커뮤니티 심리 지표
├── zentarot/           (독립 repo) 모바일 타로 앱
├── bumang-consulting/  (독립 repo, private) 인생·커리어 상담 기록
└── bumang-blog/        (독립 repo, 오케스트레이터) 이 블로그
    ├── bumang-blog-front/     (또 독립 repo)
    └── bumang-blog-backend/   (또 독립 repo)
```

여기서 세션을 열면 Claude는 개별 프로젝트의 구현자가 아니라 **포트폴리오 매니저**로 동작한다.
특정 프로젝트를 깊게 파는 게 아니라,
프로젝트 간 공통 패턴이나 스택 이탈, 재사용 가능한 자산을 짚어주는 역할이다.

문제가 하나 있었다. 하위 프로젝트들이 전부 독립 git 레포라는 것이다.
상위에 또 git repo를 만들면 하위 레포들이 딸려 들어간다.
서브모듈을 쓸까 하다가, 그냥 `.gitignore` 화이트리스트로 해결했다.
`/*`로 전부 무시한 뒤 매니저 파일만 `!`로 되살리는 방식이다.

```gitignore
/*
!.gitignore
!CLAUDE.md
!PROJECTS.md
!README.md
!memory/
!.claude/
```

이러면 나중에 새 사이드 프로젝트를 추가해도 자동으로 제외된다.
등록 절차가 없다는 게 중요하다.
사람이 기억해야 하는 절차는 언젠가 반드시 빠진다.

## 무엇을 기억하고, 무엇을 기억하지 않는가

여기서부터가 이 시스템의 핵심이다.
처음엔 나도 "맥락을 손실 없이 다 쌓자"고 생각했다.
그런데 그건 틀린 목표였다.

기억을 성질별로 갈랐다.

| 성질 | 예시 | 저장하는가 |
|---|---|---|
| 재생성 가능 | 레포 파일 트리, 커밋 모멘텀 | ❌ 필요할 때 git으로 즉석 생성 |
| 천천히 변함 | 아키텍처 지도 | 🔶 필요해질 때만 온디맨드 |
| **재생성 불가** | **의사결정 · 이유 · 스택 이탈 · 유저 성향** | ✅ 여기가 핵심 |

레포 구조가 궁금하면 `git ls-files`로 뽑으면 된다.
최근에 뭘 했는지는 `git log`가 알려준다.
그런 걸 md에 적어두면 그 순간부터 낡기 시작하고,
낡은 기록을 읽은 AI는 틀린 판단을 한다.
저장할 가치가 있는 건 **왜 그렇게 만들었는지**뿐이다.

그래서 `memory/decisions/`에는 결정만 쌓는다. 형식은 단순하다.
한 결정마다 **결정 / 이유 / 상태** 세 가지를 반드시 적는다.
특히 이유는 필수다.
나중의 내가 "왜 이렇게 갔지"를 되물을 때 답이 거기 있어야 하니까.

## 저장하지 않는 대신 매번 계산한다

그럼 "지금 어떤 프로젝트가 살아있고 어떤 게 죽었나"는 어떻게 알까.
이건 재생성 가능한 정보라 저장하지 않기로 했으니, 매번 계산하기로 했다.

`SessionStart` 훅에 스크립트를 하나 물렸다.

```bash
# .claude/session-brief.sh
root="$HOME/Work/private"

while IFS= read -r gitdir; do
  dir="${gitdir%/.git}"
  week=$(git -C "$dir" log --since='7 days ago' --oneline | wc -l)
  month=$(git -C "$dir" log --since='28 days ago' --oneline | wc -l)
  if   [ "$week" -gt 0 ];  then flame="🔥"
  elif [ "$month" -gt 0 ]; then flame="🌱"
  else                          flame="💤"; fi
  echo "## $flame $name (마지막 $last · 최근7일 ${week}커밋)"
  git -C "$dir" log -3 --date=short --format='  - %ad  %s'
done < <(find "$root" -maxdepth 3 -name .git -type d -not -path '*/node_modules/*')
```

세션을 열면 이 스크립트의 출력이 컨텍스트 맨 앞에 꽂힌다.
🔥는 이번 주에 커밋이 있는 프로젝트, 🌱는 1~4주 멈춘 것, 💤은 그 이상 휴면한 것이다.

포인트는 이게 **정적 문서가 아니라 매번 새로 계산된다**는 점이다.
그래서 절대 낡지 않는다.
그리고 `.git` 디렉토리를 동적으로 탐색하기 때문에,
새 프로젝트를 추가하면 아무것도 등록하지 않아도 자동으로 잡힌다.

훅과 스킬을 어떻게 만드는지는 예전에 따로 글로 정리한 적이 있어서 여기선 넘어간다.
다만 이 워크스페이스에도 몇 개 더 있다.
개인 레포에 회사 계정으로 push하는 걸 원천 차단하는 `PreToolUse` 훅이라든가,
블로그 초안을 저장하면 내 줄바꿈 스타일로 다시 정리하라고 지시하는 `PostToolUse` 훅 같은 것들이다.

## 정본은 하나여야 한다

문서가 여러 층에 흩어지면 금방 서로 모순되는 쓰레기가 된다.
그래서 각 층이 **무엇의 정본(正本)인지**를 명시했다.

| 층 | 정본 대상 |
|---|---|
| `bumang-workspace/CLAUDE.md` | 매니저 역할·프로토콜·스택 시그니처·포트 |
| `memory/decisions/` | 크로스프로젝트 결정만 |
| `<project>/PLANNING.md` | 그 프로젝트의 기획 결정 (무엇을·왜 만드나) |
| `<project>/CLAUDE.md` | 그 프로젝트의 실행·아키텍처 결정 |
| 백엔드 Swagger | 프론트-백 API 계약 |

원칙은 **"정본은 현장"**이다.
매니저는 하위 프로젝트의 맥락을 복제하지 않고 참조만 한다.
실제로 초기엔 프로젝트별 결정이 매니저 memory에 고여 있었는데,
나중에 전부 각 레포의 `PLANNING.md`로 이관하고 매니저 쪽은 포인터로 축소했다.

이게 왜 중요한지는 얼마 뒤에 몸으로 알게 됐다.

## 20일 동안 틀린 채로 남아 있던 한 줄

`memory/decisions/`에 이런 기록이 있었다.

> 매니저 루트를 git repo로 만들어 `bu-mang/bumang-workspace`(private)에 올림.

그런데 어느 날 확인해보니 이 레포는 **public**이었다.
`gh repo view`로 실측한 값이 그랬다.
7월 6일에 잘못 적혔고, 7월 26일에 발견됐다.
그 사이 20일 동안 나는 그 틀린 기록을 근거로 판단하고 있었던 셈이다.

다행히 사고로 이어지진 않았다.
애초에 사적인 내용은 별도 private 레포로 완전히 분리해뒀기 때문이다.
하지만 아찔했던 건, **아무도 그걸 검증하지 않았다는 사실 자체**였다.

이게 md 기반 컨텍스트 저장소의 진짜 위험이다. 용량이 아니다.
틀린 한 줄이 조용히 앉아 있다가,
그걸 읽은 AI가 자신 있게 틀린 답을 내놓는 것이다.
그래서 나는 그 블록을 지우지 않고 **정정 이력을 붙여서** 남겼다.
"원래 private라고 적혀 있었으나 틀렸다, 정본은 실측값 public이다,
그리고 이 오기는 20일간 아무도 못 잡았다"라고.

## 그런데 이거, 계속 쌓이면 다 읽을 수 있나?

시스템을 3주쯤 굴리고 나니 진짜 걱정이 생겼다.
결정이 나올 때마다 기록을 늘리고 있는데,
이러다 10만 줄짜리 메모리를 매번 읽어야 하는 상황이 오는 거 아닐까.
토큰이 아깝다기보다 **물리적으로 다 로드할 수 있는지**가 궁금했다.

막연히 걱정하는 대신 재봤다.

| 파일 | 줄 | 자 |
|---|---:|---:|
| `memory/decisions/portfolio.md` | 80 | 7,918 |
| `CLAUDE.md` | 91 | 4,370 |
| `PROJECTS.md` | 59 | 3,674 |
| `memory/preferences.md` | 22 | 1,839 |
| 기타 | 60 | 2,578 |
| **합계** | **312줄** | **20,379자** |

결정 하나가 대략 8줄이다.
그러니까 10만 줄이 되려면 결정이 12,500건 쌓여야 한다.
지금 페이스로 **62년치**다.
걱정했던 시나리오는 오지 않는다는 뜻이었다.

그런데 안심할 일이 아니었다.

## 진짜 천장은 10만 줄이 아니었다

줄당 평균 65자인데, 한국어라 대략 줄당 60~70토큰쯤 된다.
여기서 계산이 나온다.

| | 이론상 들어가는 줄 | 메모리에 쓸 만한 현실 예산 |
|---|---:|---:|
| 200K 컨텍스트 | 약 3,000줄 | **약 300줄** |
| 1M 컨텍스트 | 약 15,000줄 | **약 1,500줄** |

컨텍스트는 메모리만 담는 게 아니다. 대화도, 코드도, 툴 출력도 들어간다.
메모리가 창의 10%를 넘어가면 정작 일할 공간이 줄어든다.
그래서 현실 예산은 1,500줄 안팎이고, 내 성장률은 연 1,000~1,600줄이었다.

**즉 62년이 아니라 1~2년이면 닿는다.**
200K 창 기준으로는 이미 초과 상태였다.

게다가 더 재밌는 사실이 있었다.
Claude Code의 Read 툴은 기본적으로 **2,000줄까지만** 읽는다.
10만 줄짜리 파일을 주면 통째로 안 읽히고 잘려서 온다.
그러니까 "메모리를 다 로드한다"는 건 지금 파일이 우연히 작아서 성립하던 것이지,
시스템이 그렇게 설계된 게 아니었다.

## 압축은 답이 아니었다

처음엔 오래된 기록을 요약해서 줄일까 생각했다.
그런데 이 시스템의 저장 기준이 "재생성 불가한 것만"이었다는 걸 떠올리니 답이 나왔다.
**요약은 정확히 그 재생성 불가한 부분부터 깎아낸다.**

예를 들어 블로그 백엔드가 502를 뱉었던 장애 기록이 있다.
요약하면 이렇게 될 것이다. "디스크 포화로 502, 로그 로테이션 추가로 해결."
그런데 원본에 실제로 적힌 건 이런 것들이었다.

> ⚠️ 함정: 백엔드 포트가 compose에서 `expose`만 돼(호스트 4001 미publish) `curl localhost:4001`은 **정상적으로** 실패한다. 앱이 죽은 신호로 오독하지 말 것.

> 배포 워크플로우는 `docker-compose up -d app`(app만) 재생성이라, compose의 로깅 블록이 nginx·frontend·db엔 자동 적용 안 됨. 배포 후 서버에서 한 번 전체 `up -d` 필요.

이 두 줄이 다음번에 몇 시간을 아껴준다.
그리고 요약본에서는 절대 복원되지 않는다.
**결론과 이유는 압축하면 안 되고, 압축해도 되는 건 애초에 저장하지 말았어야 할 것들이다.**

## 진짜 문제는 monolith였다

그러다 회사 쪽 메모리 구조를 다시 봤다. 그리고 차이가 선명해졌다.

| | 회사 (camfit) | 내 워크스페이스 |
|---|---|---|
| 구조 | **33개 파일** + `MEMORY.md` 인덱스 | `portfolio.md` **한 덩어리** |
| 한 파일 | 한 가지 사실 | 결정 10개 |
| 로드 | 인덱스만 항상, 본문은 필요할 때 | **무조건 전부** |

회사 쪽은 파일이 30개가 넘어도 아무 문제가 없다.
인덱스 한 줄씩만 항상 로드되고 본문은 골라 읽기 때문이다.
전사 30~40명이 md를 쌓고도 안 터지는 이유가 양이 적어서가 아니라
**전부 로드하지 않아서**였던 것이다.

내 `portfolio.md`는 정반대였다.
한 파일이라 **선택적 로드가 원천적으로 불가능**했다.
결정 하나가 필요해도 열 개를 다 읽어야 했다.

역설적인데, 이 monolith는 **"눈에 보이게 만들겠다"는 선택의 부작용**이었다.
Claude Code에는 원래 네이티브 메모리가 있는데,
그건 작업 폴더 바깥의 숨은 경로에 저장돼서 내 눈에 안 보인다.
나는 결정 기록을 직접 보고 관리하고 싶었기 때문에 보이는 `memory/` 폴더를 정본으로 삼았고,
사람이 읽기엔 한 파일이 편하니까 자연스럽게 한 덩어리가 됐다.
그리고 그 대가로 선택적 로드를 잃었다.

## 그래서 이렇게 쪼갰다

목표를 다시 세웠다.
총량을 줄이는 게 아니라, **총량과 상시 로드량을 분리**하는 것이다.

```
memory/decisions/
├── README.md                              ← 인덱스 (항상 로드)
├── 2026-07-26-memory-sharding.md
├── 2026-07-26-docker-log-rotation.md
├── 2026-07-12-plugin-optout-per-repo.md
├── 2026-07-11-planning-first.md
├── ...
└── archive/                               ← 강등된 옛 결정
```

결정 하나가 파일 하나가 됐다.
각 파일에는 frontmatter로 `name`, `description`, `status`를 달았고,
본문은 예전과 똑같이 결정·이유·상태를 담는다.

그리고 `README.md`가 인덱스다.
결정 하나가 한 줄이고, 그 한 줄에 **결론과 핵심 함정까지** 담는다.
본문을 안 열고도 판단할 수 있어야 인덱스가 제 역할을 하기 때문이다.

```markdown
## 🔴 열린 항목

- [2026-07-26-docker-log-rotation](...) — **ant-index에 로그 로테이션 걸렸는지 점검 필요.**

## 크로스프로젝트 결정 (최신순)

- [2026-07-26-docker-log-rotation](...) — Docker Compose 개인 프로젝트는 전 서비스
  로그 로테이션 필수. 502의 진범은 로테이션 없는 json-file 로그 7.6G. 함정 2개:
  `expose`만 된 포트는 `curl localhost:4001`이 정상적으로 실패 / Actions는 app만
  재생성이라 배포 후 전체 `up -d` 필요
```

인덱스 최상단에는 **열린 항목**만 따로 뺐다.
아직 안 끝난 일이 세션을 열자마자 눈에 들어오게 하기 위해서다.

여기에 규칙 하나를 더 박았다.
**인덱스가 300줄을 넘으면** 오래된 확정 결정을 `archive/`로 강등하고,
인덱스에는 `"42건 — grep으로 조회"` 한 줄로 접는다.
이러면 결정이 몇 건이 되든 상시 로드분이 **상수로 고정**된다.

## 결과

| | 전 | 후 |
|---|---:|---:|
| **상시 로드** (매 세션) | 312줄 | **228줄** |
| 온디맨드 (필요할 때만) | 0줄 | 328줄 |
| **결정 1건 추가 시 상시 로드 증가** | **+8줄** | **+1줄** |

전체 내용은 오히려 늘었는데(문서를 보강했으니까) 매 세션 읽는 양은 27% 줄었다.
그런데 진짜 이득은 마지막 줄이다.
앞으로 결정이 쌓일 때 상시 로드 증가율이 **8배 완화**됐다.

앞서 계산했던 "1~2년이면 예산 초과"도 사라졌다.
인덱스 49줄에서 시작해 연 200줄씩 늘어 약 1.2년 뒤에 300줄 트리거에 닿고,
거기서부터는 아카이브가 흡수해서 평평해진다.
예산인 1,500줄에는 영영 안 닿는다.
**"언제 터지나"가 아니라 "300줄에서 상수"**가 된 것이다.

쪼개는 김에 정본 이중화도 하나 걷어냈다.
"스택 시그니처"와 "포트 레지스트리" 두 블록이 `CLAUDE.md`에도 똑같이 있었는데,
규칙으로 승격시켜놓고 로그 쪽 원본을 안 내린 상태였다.
863자를 지우고 인덱스에 "규칙으로 승격됨 → `CLAUDE.md`가 정본" 포인터만 남겼다.
원문이 궁금하면 git 히스토리에 그대로 있다.

## 정리하며

이 작업을 하면서 얻은 게 몇 가지 있다.

**메모리 설계의 핵심은 무엇을 저장할까가 아니라 무엇을 저장하지 않을까다.**
파일 트리, 커밋 로그, 활동 상태는 전부 재생성 가능하니까 저장하지 않고 훅으로 매번 계산한다.
이런 걸 쌓기 시작하면 md 더미는 순식간에 낡아서 오히려 해가 된다.

**정본은 반드시 하나여야 한다.**
같은 내용이 두 곳에 있으면 한쪽이 낡고, 낡은 쪽을 읽은 AI가 틀린 컨설팅을 한다.
public/private 오기가 20일간 살아있었던 게 그 증거다.

**용량 걱정은 대체로 틀린 걱정이다.**
진짜 고장은 컨텍스트 한계보다 훨씬 먼저 온다.
관련 없는 기록 사이에서 관련 있는 하나를 덜 정확하게 집게 되는 주의 희석,
검증되지 않은 채 방치된 모순,
무거워져서 실제로는 안 지켜지는 회상 규칙.
컨텍스트 한계는 그 다음 문제고, 심지어 부딪혀도 터지지 않는다.
자동 압축이 조용히 요약해버릴 뿐이다. 그게 더 무섭다.

**그리고 크기 문제는 압축이 아니라 계층화로 푼다.**
10만 줄을 5만 줄로 줄여도 여전히 못 읽는다.
반면 인덱스와 아카이브를 두면 100만 줄이어도 300줄만 읽는다.
자릿수가 다른 해법이다.

회사에서 본 시스템이 신박했던 건 md를 많이 쌓아서가 아니었다.
**필요한 것만 꺼내 읽을 수 있게 설계돼 있어서**였다는 걸, 내 걸 만들어보고 나서야 알았다.
쌓는 건 하루면 되는데, 안 쌓는 규율을 세우는 데는 3주가 걸렸다.
