블로그 속도 문제를 고치다가 인증 코드를 열어볼 일이 생겼다.
그런데 열어보니 손댈 곳이 한두 군데가 아니었다.

이 인증은 Next.js App Router를 제대로 이해하기 전에 만든 것이다.
그 뒤로는 문제가 생길 때마다 덧대기만 해 왔다.
9월에도 "자꾸 로그아웃된다"는 문제를 쫓다가 원인 하나만 고치고 덮어 둔 상태였다.

그래서 이번엔 Claude Code에게 리뷰를 맡기고,
"가장 보편적으로 선호되는 방식이 뭔가"부터 다시 따져 본 뒤 통째로 다시 짰다.


## 맥에서 로그인하면 폰이 로그아웃됐다
원래 구조의 뼈대는 나쁘지 않았다.
백엔드(NestJS)가 access JWT와 refresh JWT를 httpOnly 쿠키로 내려주고,
브라우저 JS는 토큰을 직접 만지지 않는다.
문제는 그 위에 얹힌 것들이었다.

먼저 refresh 토큰을 `users` 테이블의 컬럼 하나에 평문으로 저장하고 있었다.
계정당 딱 한 칸이다.

그러니 맥에서 로그인하고 폰에서 다시 로그인하면 폰의 토큰이 그 칸을 덮어쓴다.
맥이 다음에 토큰을 갱신하려고 하면 DB의 값과 맞지 않고,
백엔드는 "토큰이 이상하다"며 DB의 토큰까지 지워버렸다.

결과적으로 기기 두 대가 모두 로그아웃됐다.
9월에 겪은 잦은 로그아웃의 원인 중 하나가 이거였다.

서버 로그도 문제였다.
갱신 요청이 올 때마다 백엔드가 이런 로그를 찍고 있었다.

```ts
console.log('🌍 Extracted refreshToken:', token);
```

30일짜리 refresh 토큰 전체가 로그에 남는다.
서버에 접속할 수 있는 사람이라면 로그만 보고 내 계정으로 로그인할 수 있었다는 뜻이다.
디버깅하려고 넣었다가 그대로 남은 흔적이다.
(이모지까지 붙여 놓은 걸 보면 꽤 신나게 디버깅했던 모양이다...)

프론트는 JWT 서명 키를 들고 있었다.
Next.js 미들웨어가 토큰을 직접 검증하겠다고
백엔드와 같은 `JWT_SECRET`을 프론트 서버 환경변수에 두고 있었던 것이다.

브라우저로 새어 나간 건 아니었다.
빌드 결과물을 뒤져 보니 브라우저로 가는 파일 139개 중 이 값이 들어간 건 없었다.

그래도 이 키는 검증만 하는 키가 아니라 **토큰을 발급할 수도 있는 키**다.
프론트 서버가 뚫리면 아무 계정, 아무 권한의 토큰이나 만들 수 있었다.


## 첫 화면은 항상 비로그인으로 떴다
로그인 상태를 알아내는 방식도 이상했다.

헤더 컴포넌트가 브라우저에서 `/users/me`를 호출해 zustand 스토어에 사용자 정보를 넣고,
다른 컴포넌트들은 그게 채워지기를 기다렸다.
그러다 보니 첫 화면은 항상 비로그인 모양으로 떴다가 잠시 뒤 닉네임으로 바뀌었다.

"아직 모름"을 뜻하는 `isAuthLoading`을 기다리는 코드가
관리자 페이지 세 곳, 글 상세, 헤더에 흩어져 있었다.
프로필 조회가 실패한 경우를 "비로그인 확정"으로 치려고
ErrorBoundary로 우회하는 코드까지 생겨 있었다.

더 아까운 건 익명 방문자였다.
쿠키가 없는 방문자가 페이지를 열면 프로필 조회가 401로 실패한다.
그러면 axios 인터셉터가 그걸 받아 토큰 갱신을 시도했다가 또 401을 받는다.

**익명 방문자가 페이지를 열 때마다 실패하는 API 호출이 두 번씩** 나가고 있었던 것이다.
내 블로그 방문자의 99%는 익명인데.


## 그럼 가장 보편적인 방식은 뭘까
Next.js App Router에 별도 백엔드가 붙는 구성에서 권장되는 원칙은 세 가지로 모인다.

**인증의 권위는 백엔드 한 곳에 둔다.**
프론트는 서명 키를 갖지 않는다.
미들웨어는 "쿠키가 있나, 역할이 뭔가" 정도만 빠르게 보고 리다이렉트만 한다.
실제로 데이터를 막는 건 백엔드의 가드다.

**사용자 정보는 서버에서 확정해 내려준다.**
레이아웃이 요청마다 현재 사용자를 조회하고, 그 값을 클라이언트에 넘긴다.
그러면 "아직 모름" 상태 자체가 사라진다.

**브라우저는 토큰을 모른다.**
httpOnly 쿠키만 오가고, 갱신은 정해진 곳에서만 한다.

다행히 마지막 원칙은 원래도 지키고 있었다.
앞의 둘을 맞추고, refresh 토큰 저장 방식을 고치는 게 이번 작업의 범위가 됐다.

## 잠깐, 세션 방식으로 바꾸자는 건가?
Claude가 "기기별 세션 테이블을 만들자"고 했을 때 순간 헷갈렸다.
JWT를 버리고 세션 방식으로 가자는 건가?

그런데 따져 보면 원래 구조도 이미 절반은 세션 방식이었다.
refresh 토큰을 DB에 저장하고, 갱신할 때마다 DB 값과 대조했으니까.
서버가 로그인 상태를 기억하고 있었다는 뜻이다.
| | 세션 방식 | JWT 방식 |
|---|---|---|
| 서버가 로그인 상태를 저장 | 함 | 안 함 |
| 클라이언트가 가진 것 | 의미 없는 번호표 | 정보가 적힌 서명된 신분증 |
| 즉시 취소 | 됨 | 안 됨 |
이 기준으로 보면 access 토큰이 JWT 방식이고, refresh 토큰이 세션 방식이다.
사실 로그아웃이 되는 JWT 인증은 거의 다 이런 반반 구조다.
refresh 토큰을 저장하지 않으면 로그아웃을 구현할 방법이 없기 때문이다.

그러니 새로 세션을 도입한 게 아니다.
이미 있던 세션 성격을 제대로 된 모양으로 정리한 것이다.

`refresh_session_entity` 테이블을 새로 만들었다.
로그인 한 번이 행 하나다.

```ts
@Entity('refresh_session_entity')
export class RefreshSessionEntity {
  @PrimaryGeneratedColumn() id: number;

  @Index() @Column({ type: 'int' }) userId: number;

  // refresh 토큰의 SHA-256. 원문은 저장하지 않는다.
  @Index({ unique: true }) @Column({ length: 64 }) tokenHash: string;

  // 마지막 사용 시점 + 30일. 갱신할 때마다 밀린다.
  @Index() @Column({ type: 'timestamp' }) expiresAt: Date;

  @Column({ type: 'timestamp' }) lastUsedAt: Date;
  @Column({ length: 45, nullable: true }) ip: string | null;
  @Column({ type: 'text', nullable: true }) userAgent: string | null;
}
```

맥과 폰이 각자 행을 가지니 서로를 덮어쓸 일이 없다.
한 기기에서 로그아웃하면 그 기기의 행만 지워진다.

토큰 원문 대신 해시를 저장하니 DB가 유출돼도 그 값으로는 로그인할 수 없다.
유저당 최대 10개까지만 두고, 만료된 행은 자정 크론이 정리한다.


## refresh 토큰은 왜 JWT가 아니게 됐나
refresh 토큰을 JWT 대신 256비트 무작위 문자열로 바꿨다.
이 부분은 나도 고개를 갸웃했다.
튜토리얼에서는 보통 access와 refresh를 둘 다 JWT로 만드니까.

그런데 JWT가 왜 쓰이는지를 생각하면 답이 나온다.

JWT는 내용을 암호화한 게 아니다.
헤더와 내용은 base64로 표기만 바꾼 것이라 누구나 읽을 수 있다.
시크릿 키는 내용을 숨기는 데가 아니라 위조를 막는 서명에 쓰인다.

즉 JWT의 가치는 **"DB를 안 보고도 서명만으로 믿을 수 있다"**는 데 있다.
access 토큰이 JWT인 이유가 그거다.
모든 API 요청마다 DB를 조회하지 않아도 된다.

refresh 토큰은 사정이 다르다.
로그아웃하면 즉시 무효가 돼야 하니 어차피 DB를 봐야 한다.
DB를 볼 거라면 서명 검증은 중복이고,
`JWT_REFRESH_SECRET`이라는 관리할 키만 하나 늘어난다.

게다가 JWT는 만료 시각이 토큰 안에 박혀 있다.
"쓸 때마다 30일 연장"을 하려면 매번 새 토큰을 발급해야 한다.
무작위 문자열이면 DB의 만료 시각만 밀면 된다.
| | access 토큰 | refresh 토큰 |
|---|---|---|
| 쓰는 빈도 | 모든 API 요청 | 15분에 한 번 |
| DB 조회 | 피하고 싶음 | 어차피 해야 함 |
| 맞는 형태 | JWT | 무작위 문자열 |
OAuth 2.0 표준도 refresh 토큰의 형태를 정하지 않는다고 한다.
"둘 다 JWT"는 흔한 구현이지 따라야 하는 규칙은 아니었다.


## 쓸 때마다 토큰을 바꾸지는 않는다
refresh 토큰을 쓸 때마다 새 값으로 바꾸는 로테이션이라는 방식도 있다.
같은 토큰이 두 번 쓰이면 탈취로 보고 세션을 끊을 수 있어서 보안상 장점이 있다.
하지만 이건 넣지 않았다.

Next.js는 링크에 마우스를 올리기만 해도 페이지를 미리 불러오고,
필요 없어지면 그 요청을 취소한다.

만약 새 refresh 토큰을 실은 응답이 브라우저에 도착하기 전에 취소되면 어떻게 될까?
브라우저는 옛 토큰을 들고 있고, 서버는 새 토큰만 인정하게 된다.
멀쩡한 로그인이 끊기는 것이다.

9월에 겪은 "잦은 로그아웃"을 내 손으로 다시 만드는 셈이다.
그래서 토큰 값은 고정하고 만료 시각만 연장한다.

```ts
async renewAccessToken(refreshToken: string) {
  const session = await this.sessionRepo.findOne({
    where: { tokenHash: this.hashToken(refreshToken) },
  });
  if (!session) return null;

  const now = new Date();
  if (session.expiresAt <= now) {
    await this.sessionRepo.delete(session.id);
    return null;
  }

  // 역할은 토큰이 아니라 DB의 현재 값으로 다시 읽는다.
  const user = await this.usersService.validateOneUserById(session.userId);

  await this.sessionRepo.update(session.id, {
    lastUsedAt: now,
    expiresAt: new Date(now.getTime() + REFRESH_TOKEN_TTL_SEC * 1000),
  });

  return { accessToken: this.generateAccessToken(user.id, user.email, user.role) };
}
```

갱신할 때 역할을 DB에서 다시 읽는다는 점도 작은 개선이다.
예전 refresh JWT에는 역할이 박혀 있어서,
권한을 바꿔도 30일 동안 옛 권한이 따라다닐 수 있었다.
지금은 늦어도 15분 뒤 다음 갱신 때 반영된다.


## 로그인 상태는 서버에서 확정한다
프론트에서 가장 크게 바뀐 건 로그인 상태를 알아내는 위치다.
헤더가 브라우저에서 조회하던 것을 루트 레이아웃이 서버에서 하도록 옮겼다.

```tsx
// app/[locale]/layout.tsx (서버 컴포넌트)
const user = await getCurrentUser();

return (
  // ...
  <AuthProvider user={user}>
    <Header />
    {children}
  </AuthProvider>
);
```

`getCurrentUser()`는 쿠키가 없으면 백엔드를 아예 부르지 않고 `null`을 돌려준다.
익명 방문자의 실패 호출 두 번이 0번이 된 이유다.

컴포넌트에서는 이것만 쓰면 된다.

```tsx
const { user, isAuthenticated } = useAuth();
```

여기서 하나 헷갈렸던 게 있다.
`useAuth`는 `"use client"`가 붙은 클라이언트 훅이다.
그런데 어떻게 첫 화면부터 정확한 값을 받을 수 있지?

답은 **`"use client"`가 "브라우저에서만 실행"이라는 뜻이 아니라는 것**이었다.
클라이언트 컴포넌트도 첫 HTML을 만들 때 서버에서 한 번 실행되고,
그 뒤 브라우저에서 다시 이어받는다.

서버 컴포넌트가 넘긴 props는 직렬화돼서 HTML과 함께 브라우저로 간다.
그래서 서버 실행과 브라우저 실행이 같은 값으로 같은 결과를 낸다.
화면이 바뀔 일이 없는 것이다.

사용자 정보를 zustand가 아니라 React context에 둔 것도 이유가 있다.
서버에서 모듈 전역 스토어는 요청끼리 공유된다.
거기 사용자 정보를 넣으면 다른 방문자의 정보가 섞일 수 있다.
context는 요청마다 따로 만들어진다.

결과적으로 zustand 인증 스토어와 `isAuthLoading`을 기다리던 코드들이 전부 사라졌다.
140줄쯤 되던 헤더 파일이 40줄이 됐다.

다만 한계도 있다.
Next.js는 링크로 이동할 때 공통 레이아웃을 다시 그리지 않는다.
그래서 다른 탭에서 로그아웃해도 이 탭은 새로고침 전까지 로그인 모양으로 남는다.

레이아웃의 값은 화면 표시에만 쓰고 실제 차단은 백엔드가 하니 보안 문제는 아니다.
로그인과 로그아웃을 전체 새로고침으로 끝내는 것도 이 값을 다시 받기 위해서다.


## 미들웨어는 서명을 확인하지 않는다
미들웨어에서 `JWT_SECRET`을 빼고 나면, 토큰이 진짜인지는 어떻게 아나?
답은 **미들웨어는 몰라도 된다**는 것이다.

```ts
// 서명은 검증하지 않고 만료 시각과 역할만 읽는다.
function readAccessClaims(token: string | undefined): AccessClaims | null {
  if (!token) return null;
  try {
    const payload = token.split(".")[1];
    const bytes = Uint8Array.from(
      atob(payload.replace(/-/g, "+").replace(/_/g, "/")),
      (c) => c.charCodeAt(0),
    );
    const claims = JSON.parse(new TextDecoder().decode(bytes));
    return { role: claims.role ?? null, expiresAt: claims.exp * 1000 };
  } catch {
    return null;
  }
}
```

미들웨어가 하는 일은 두 가지뿐이다.
access 토큰이 만료됐으면 refresh 쿠키로 갱신하고,
`/admin`이나 `/blog/edit`에 역할이 안 맞으면 리다이렉트한다.

정말 그래도 괜찮은지 직접 시험해 봤다.
역할을 `host`로 꾸민 가짜 토큰을 만들어 `/admin`에 들어가 본 것이다.

미들웨어는 서명을 안 보니 통과시킨다.
하지만 레이아웃이 백엔드에 "이 사람 누구냐"고 물으면 백엔드가 서명을 검증해 거부한다.
화면에는 사용자 정보 없는 403이 뜬다.
위조 토큰으로 얻을 수 있는 건 빈 화면뿐이다.

9월에 고친 원칙은 그대로 지켰다.
**백엔드가 401로 세션을 거부했을 때만 쿠키를 지운다.**

500이나 연결 실패는 "세션이 무효"가 아니라 "서버에 문제가 있다"는 뜻이다.
그럴 땐 쿠키를 그대로 두고 그 페이지만 비로그인 모양으로 그린다.
서버가 돌아오면 다음 페이지 이동에서 다시 로그인 상태가 된다.


## rate limit은 설정만 있고 걸려 있지 않았다
같이 정리하다가 하나 더 나왔다.

백엔드에 `ThrottlerModule` 설정은 있었는데,
실제로 적용하는 가드가 가입과 로그인 두 곳에만 붙어 있었다.
나머지 API에는 제한이 아예 없었던 것이다.

```ts
providers: [
  // 모듈 설정만으로는 제한이 걸리지 않는다. 가드를 전역 등록해야 실제로 동작한다.
  { provide: APP_GUARD, useClass: CfThrottlerGuard },
],
```

가드를 `APP_GUARD`로 전역 등록하고,
프론트 미들웨어가 메모리 Map으로 흉내 내던 rate limit은 지웠다.

테스트가 잡아낸 함정도 하나 있었다.
백엔드의 `types/` 폴더에 있던 유일한 파일을 지웠더니,
빌드 결과물 위치가 `dist/src/main.js`에서 `dist/main.js`로 바뀐 것이다.

TypeScript가 출력 위치를 소스들의 공통 상위 폴더로 추측하기 때문이다.
그대로 배포했다면 서버가 시작 파일을 못 찾았을 것이다.
`tsconfig`에 `rootDir`를 고정해서 막았다.


## 정리
| 항목 | 이전 | 이후 |
|---|---|---|
| refresh 토큰 저장 | 계정당 1칸, 평문 | 기기별 세션, 해시 |
| 기기 두 대 사용 | 서로 로그아웃시킴 | 서로 무관 |
| 토큰 수명 | access 1시간, refresh 고정 30일 | access 15분, refresh 마지막 사용 후 30일 |
| 프론트의 서명 키 | 보유 | 없음 |
| 서버 로그의 토큰 | 매 갱신마다 전체 출력 | 없음 |
| 첫 화면의 로그인 상태 | 비로그인 → 잠시 뒤 바뀜 | 처음부터 정확 |
| 익명 방문자의 실패 호출 | 페이지마다 2번 | 0번 |
| Rate limit | 가입·로그인만 | 전체 API |
돌아보면 원래 구조의 뼈대가 틀렸던 건 아니었다.
httpOnly 쿠키, access와 refresh의 분리는 처음부터 맞게 잡혀 있었다.
문제는 그 위에 "일단 돌아가게" 얹은 것들이었다.

계정당 한 칸짜리 저장소, 디버깅하다 남긴 로그,
프론트에서 직접 해보려던 검증, 브라우저에서 뒤늦게 알아내는 로그인 상태.
하나하나는 작았는데 합쳐 놓으니 로그아웃이 잦고 화면이 깜빡이는 인증이 돼 있었다.

아직 남은 것도 있다.
refresh 토큰이 탈취되면 지금은 그 기기에서 로그아웃하는 것 말고는 대응 수단이 없다.
"모든 기기 로그아웃"이나 비밀번호 변경 같은 것들이다.

그래도 세션이 행으로 나뉘어 있으니 붙이기는 어렵지 않다.
모를 때 만든 걸 알고 나서 다시 보는 일은 꽤 부끄럽고, 꽤 재밌었다.
