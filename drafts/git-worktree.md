# git worktree, 이제는 익혀야 할 때가 됐다

## 들어가며

git을 몇 년씩 써온 사람도 `git worktree`는 한 번도 안 건드려본 경우가 많다.
얼마 전까지의 내가 딱 그랬다.

브랜치를 오갈 땐 `checkout` 하나면 충분했다.
한 사람이 물리적으로 신경 쓸 수 있는 코드베이스는 어차피 한 개였으니까.
작업하던 걸 잠깐 밀어두고 다른 브랜치로 넘어갔다가 돌아오는 흐름에
큰 불편을 못 느꼈다.

그런데 AI 에이전트가 대신 코딩을 해주는 시대가 오면서 상황이 달라졌다.
에이전트 세션 여러 개가 동시에 각자의 브랜치에서 코드를 짜는 병렬 작업이 현실이 됐고,
그러자 여러 브랜치를 물리적으로 나눠서 관리할 필요가 급격히 커졌다.
새로 옮긴 회사의 개발팀도 워크트리를 적극적으로 쓰고 권장하고 있었다.
이 흐름을 보고 나서야 나도 뒤늦게 `git worktree`를 제대로 파기 시작했다.

그래서 이 글에서는 `git worktree`가 무엇인지부터,
실제로 어떻게 쓰는지까지를 정리해두려 한다.

## git worktree가 뭔가

먼저 워크트리(worktree)라는 말부터 짚고 가자.
Git에서 워크트리는 실제 파일들이 놓여 있는 작업 디렉토리를 가리킨다.
우리가 평소에 코드를 열고 고치고 저장하는 바로 그 폴더다.

보통 저장소를 클론하면 `.git` 폴더와 함께 워크트리 하나가 만들어진다.
그리고 우리는 그 안에서 파일을 수정하고, 스테이징하고, 커밋한다.
대부분의 사람에게 "저장소 = 워크트리 하나"라는 그림이 굳어져 있는 이유다.

`git worktree` 명령어는 이 기본 구조를 확장한다.
하나의 저장소에 작업 디렉토리를 여러 개 매달 수 있게 해주는 것이다.
각 워크트리는 서로 다른 브랜치를 체크아웃한 채, 완전히 독립적으로 굴러간다.
한 폴더에서는 `main`을, 옆 폴더에서는 `feature/login`을
동시에 펼쳐놓고 작업할 수 있다는 뜻이다.

여기서 중요한 건 **`.git` 폴더는 여전히 하나라는 점**이다.
커밋 객체, 브랜치 참조, 설정 같은 Git 메타데이터를 담은 `.git`은
모든 워크트리가 공유한다.
워크트리를 아무리 늘려도 `.git`까지 이원화·삼원화되진 않는다.
그래서 한 워크트리에서 커밋한 내용은 다른 워크트리에서 곧바로 접근할 수 있다.
히스토리도, 브랜치 정보도, 설정도 전부 한 몸을 공유하기 때문이다.

## 왜 git worktree를 쓰는가

워크트리가 진가를 드러내는 상황이 몇 가지 있다.

가장 흔한 건 급한 핫픽스다.
새 기능을 한창 개발하던 중에 프로덕션에서 버그가 터졌다고 해보자.
워크트리 하나로만 일하고 있었다면,
지금까지의 변경을 stash로 밀어두거나 어정쩡하게 커밋한 다음에야
다른 브랜치로 넘어갈 수 있다.
워크트리를 쓰면 이 과정을 건너뛴다.
하던 작업은 그대로 둔 채 별도의 워크트리에서 곧장 핫픽스에 착수하면 된다.

코드 리뷰에서도 유용하다.
동료의 PR을 눈으로만 보는 게 아니라 실제로 돌려보고 싶을 때가 있다.
이때 지금 작업 중인 브랜치를 건드리지 않고,
리뷰 대상 브랜치를 별도 워크트리에 체크아웃해서 띄워볼 수 있다.
내 작업 환경은 그대로 살아 있는 채로 남의 코드를 실행해볼 수 있는 것이다.

서로 관련 없는 여러 기능을 동시에 굴려야 할 때도 좋다.
기능마다 워크트리를 따로 두면
브랜치를 갈아탈 때마다 치르던 컨텍스트 스위칭 비용이 크게 줄어든다.
그리고 바로 이 성질 덕분에,
워크트리는 여러 AI 에이전트 세션이 병렬로 일하기에 최적의 구조가 된다.
세션마다 독립된 디렉토리를 하나씩 쥐여주면,
서로의 작업물을 밟지 않고 각자의 브랜치를 마음껏 헤집을 수 있기 때문이다.

## 워크트리 생성

새 워크트리를 추가하는 기본 명령어는 `git worktree add`다.

```sh
$ git worktree add <경로> <브랜치명>
```

예를 들어 `main` 브랜치용 워크트리를 상위 디렉토리에 만들려면 이렇게 한다.

```sh
$ git worktree add ../bumang-main main
```

이러면 `../bumang-main` 디렉토리가 생기고, 그 안에 `main` 브랜치가 체크아웃된다.

새 브랜치를 만들면서 동시에 워크트리를 뽑을 수도 있다.
브랜치명을 생략하면 경로의 마지막 디렉토리 이름을 그대로 브랜치명으로 삼아
새 브랜치를 만든다.

```sh
$ git worktree add ../hotfix
```

이 명령어는 `hotfix`라는 새 브랜치를 만들고,
`../hotfix` 디렉토리에서 그 브랜치를 체크아웃한다.
디렉토리 이름과 다른 브랜치명을 쓰고 싶다면 `-b` 옵션을 붙이면 된다.

```sh
$ git worktree add -b feature/new-feature ../feature-worktree
```

이렇게 하면 `feature/new-feature` 브랜치가 새로 생기고,
`../feature-worktree` 디렉토리에서 곧장 작업을 시작할 수 있다.

한 가지 관례가 있다.
워크트리 디렉토리는 보통 기존 저장소 디렉토리 바깥에 만드는 걸 권장한다.
저장소 안에 만들면 Git이 그 폴더를 추적하려 들어서
`.gitignore`에 따로 넣어줘야 하는 번거로움이 생기기 때문이다.

## 워크트리 목록 확인

지금 저장소에 매달린 워크트리를 전부 보려면 `list`를 쓴다.

```sh
$ git worktree list
```

결과는 대략 이런 모양으로 나온다.

```sh
/Users/bumang/projects/bumang-blog       a1b2c3d [main]
/Users/bumang/projects/bumang-main       e4f5g6h [feature/login]
/Users/bumang/projects/feature-worktree  i7j8k9l [feature/new-feature]
```

각 줄은 워크트리의 경로, HEAD 커밋 해시,
그리고 현재 체크아웃된 브랜치를 차례로 보여준다.

## 워크트리 간 이동

생성된 워크트리는 그냥 평범한 디렉토리이므로, 이동은 `cd` 한 방이면 된다.
별도의 마법 같은 명령어가 있는 게 아니다.

각 워크트리는 완전히 독립된 작업 환경이라,
IDE나 에디터에서 워크트리 디렉토리를 각각 별도의 창이나 프로젝트로 열어서 쓰면 된다.
터미널 탭을 나눠 워크트리마다 하나씩 붙여두면,
브랜치를 오간다는 감각 없이 그냥 탭만 바꾸면 다른 작업이 펼쳐진다.

## 워크트리 삭제

더 이상 쓸 일이 없는 워크트리는 `remove`로 지운다.

```sh
$ git worktree remove <worktree-경로>
```

앞에서 만든 피처 워크트리를 지운다면 이렇게 한다.

```sh
$ git worktree remove ../feature-worktree
```

만약 워크트리에 커밋되지 않은 변경이 남아 있으면 Git이 경고를 띄운다.
이때는 `-f` 또는 `--force`로 강제 삭제할 수 있다.

```sh
$ git worktree remove --force ../feature-worktree
```

`rm -rf`처럼 워크트리 디렉토리를 손으로 직접 지워버린 경우엔
`prune`으로 뒤처리를 해줘야 한다.

```sh
$ git worktree prune
```

이 명령어는 이제 존재하지 않는 워크트리 디렉토리를 가리키던 참조를 정리해준다.
지워진 폴더의 흔적이 `.git` 안에 유령처럼 남는 걸 막아주는 셈이다.

## 실전 활용: 코드 리뷰

명령어만 나열하면 감이 잘 안 오니, 실제 시나리오로 엮어보자.
동료가 올린 PR을 직접 실행해보면서 리뷰하고 싶은 상황이다.
내가 지금 짜던 코드는 손대지 않은 채로 말이다.

```sh
# 리뷰 대상 브랜치를 위한 워크트리 생성
$ git fetch origin
$ git worktree add ../review-pr123 origin/feature/payment

# 리뷰 워크트리로 이동해서 실제로 돌려본다
$ cd ../review-pr123
$ npm install
$ npm run dev

# 리뷰가 끝나면 워크트리만 정리
$ cd ../bumang-blog
$ git worktree remove ../review-pr123
```

핵심은 이 모든 과정 동안 내 원래 작업 디렉토리는 전혀 흔들리지 않았다는 점이다.
stash도, 커밋도 필요 없이 남의 브랜치를 통째로 실행해보고,
다 보고 나면 워크트리만 걷어내면 된다.

## 주의사항

편리한 만큼 알아둬야 할 함정도 몇 가지 있다.

먼저, 같은 브랜치를 두 워크트리에서 동시에 체크아웃할 수는 없다.
워크트리끼리 같은 브랜치를 붙들고 충돌을 일으키는 걸 막기 위한 제약이다.
이미 다른 워크트리가 잡고 있는 브랜치를 또 체크아웃하려 하면
아래처럼 거절당한다.

```sh
$ git worktree add ../another-main main
fatal: 'main' is already checked out at '/Users/bumang/projects/bumang-main'
```

그리고 앞에서도 언급했듯,
워크트리 디렉토리를 저장소 내부에 만들면 Git이 그 폴더를 추적하려 든다.
되도록 저장소 바깥에 만드는 편이 마음이 편하다.

마지막 하나는 IDE 관련이다.
워크트리 디렉토리는 진짜 `.git` 폴더 대신,
메인 저장소를 가리키는 `.git` 파일 하나만 들고 있다.
이 차이 때문에 일부 IDE는 워크트리를 Git 저장소로 제대로 인식하지 못하기도 한다.
이럴 땐 해당 워크트리 디렉토리를 IDE에서 아예 별도의 프로젝트로 열면 된다.
VS Code나 그 계열의 포크 에디터라면,
워크트리마다 창을 따로 띄우는 것만으로 대개 문제없이 동작한다.

## git stash와 비교

여러 브랜치를 오갈 때 가장 익숙한 방법은 아무래도 `git stash`다.
하던 변경을 잠깐 저장해두고, 다른 브랜치로 넘어가서 볼일을 본 뒤,
원래 브랜치로 돌아와 `git stash pop`으로 꺼내는 방식이다.

문제는 이게 자주 반복되면 은근히 번거롭다는 데 있다.
stash를 여러 개 쌓다 보면 어떤 게 무슨 작업이었는지 헷갈리고,
엉뚱한 브랜치에서 `pop`을 눌러 사고를 치기도 한다.
나도 stash 스택을 잘못 건드려 한참을 헤맨 적이 있다.

`git worktree`는 이 문제를 아예 발생하지 않게 만든다.
브랜치마다 물리적인 디렉토리가 따로 있으니,
변경을 임시로 숨겼다 꺼내는 절차 자체가 사라진다.
stash로 저글링하는 게 아니라,
그냥 터미널 탭을 바꾸면 그 자리에 다른 브랜치의 작업이 그대로 놓여 있다.

## git clone과 비교

"그러면 그냥 저장소를 여러 번 클론하면 되는 거 아닌가?"라는 의문이 들 수 있다.
실제로 그렇게 쓰는 사람도 있다.

물론 클론을 여러 개 두는 것도 방법이지만,
`git worktree`가 나은 지점이 분명히 있다.
우선 모든 워크트리가 `.git`을 공유하기 때문에,
대용량 저장소에서 디스크를 크게 아낄 수 있다.
클론을 세 번 뜨면 무거운 히스토리도 세 벌이 되지만,
워크트리는 그 부담이 한 벌뿐이다.
또한 한 워크트리에서 커밋하면 나머지 워크트리가 즉시 그 결과를 볼 수 있어서,
클론들 사이를 오가며 fetch/pull로 동기화할 필요가 없다.
저장소 설정도 공유되고,
무엇보다 하나의 저장소로 모든 작업 디렉토리를 관리하니
머릿속이 훨씬 깔끔하다.
