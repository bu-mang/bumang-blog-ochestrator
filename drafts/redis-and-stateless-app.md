# Redis를 파다가 깨달은 것 — 앱은 복제되고, 데이터 서버는 공유된다

새로 옮긴 회사에서는 Redis를 꽤 적극적으로 쓰고 있었다.
멱등 처리, 분산 락, Bull로 도는 메시지 큐까지.
이름은 익숙했지만 정작 "왜 굳이 Redis로 이걸 하는가"를 제대로 설명하라면 막막했다.
그러다 특정 데이터를 생성하는 로직에 멱등 처리를 직접 붙여볼 일이 생겼고,
그참에 Redis가 뭔지, 왜 나왔고 어디에 쓰는지를 처음부터 정리해보게 됐다.

그런데 캐시, rate limiting, 큐, 분산 락을 하나씩 짚다 보니 엉뚱하게도 예전에 겪었던 버그 하나의 정체가 선명해졌다.
크론잡이 배포한 앱 개수만큼 여러 번 실행되던 그 일.
당시엔 "왜 이러지" 하고 넘겼는데,
Redis를 이해하고 나니 그게 분산 시스템의 아주 기본적인 성질에서 나온 필연이었다는 게 보였다.
회사에서 Redis로 멱등 처리와 분산 락을 쓰는 이유도 결국 같은 뿌리였다.
그래서 이 글은 Redis 소개로 시작하지만,
사실은 그 깨달음에 이르는 과정에 대한 글이다.

## Redis는 왜 나왔나

Redis는 메모리(RAM)에 데이터를 올려두고 쓰는 key-value 저장소다.
이름 자체가 REmote DIctionary Server의 약자다. 핵심은 한 문장으로 끝난다.
디스크가 아니라 메모리에 있으니까 압도적으로 빠르다. 일반적인 RDB 조회가 밀리초 단위라면 Redis는 마이크로초 단위로 응답한다.

만든 사람(antirez)의 계기부터가 실무 문제였다. 웹 로그 분석 서비스에서 실시간으로 페이지뷰 같은 통계를 계속 갱신해야 했는데,
당시 주력이던 관계형 DB로는 감당이 안 됐다. 관계형 DB는 데이터를 디스크에 안전하고 정합성 있게 저장하는 데 최적화돼 있다.
트랜잭션, 조인, 복잡한 쿼리 — 다 강력하지만 그만큼 무겁다.
"숫자 하나를 초당 수천 번 +1 하는" 단순하고 폭발적으로 잦은 작업에는 오버스펙이고 느리다.

그래서 나온 발상이 "자주 쓰는 데이터는 그냥 메모리에 두면 안 되나"였다.
사실 이 아이디어 자체는 이미 Memcached라는 메모리 캐시가 구현하고 있었다.
Redis가 한 일은 여기서 두 걸음 더 나간 것이다.

첫째, 값으로 단순 문자열뿐 아니라 리스트·셋·정렬된 셋·해시 같은 자료구조를 저장할 수 있게 했다.
"메모리에 올린 캐시"를 넘어 "메모리에서 도는 자료구조 서버"가 된 것이다.

둘째, 주기적으로 스냅샷을 뜨거나 명령 로그를 남겨서 재시작해도 데이터를 복구할 수 있게 했다.
단순 휘발성 캐시가 아니라 진짜 저장소로도 쓸 수 있게 된 것이다.

그래서 "Redis는 캐시 DB다"라는 말은 반은 맞고 반은 틀리다.
가장 흔한 용도가 캐시인 건 맞지만, 뒤에서 볼 큐·Pub/Sub·분산 락·세션 저장소는 캐시가 아니다.
정확히 말하면 Redis는 인메모리 자료구조 저장소이고, 그중 가장 널리 쓰이는 용도가 캐시다.
"레디스 = 캐시"는 "포토샵 = 사진 자르는 프로그램"이라고 하는 것과 비슷하다. 틀린 말은 아닌데 도구를 너무 좁게 가둔다.

## 캐시부터 — 가장 흔한 용도

NestJS 백엔드를 기준으로 보자.
포스트 상세 조회는 조회수는 많은데 내용은 자주 안 바뀐다. 전형적인 캐시 대상이다.
캐시가 없으면 매 요청마다 DB로 가서 조인하고 연산한다.

```typescript
async getPost(id: number) {
  return this.postRepository.findOne({
    where: { id },
    relations: ['category', 'tags', 'blocks'],
  });
}
```

캐시를 붙이면 흐름이 바뀐다.
먼저 Redis에 물어보고, 있으면 DB에 가지 않고 바로 반환한다.
없을 때(cache miss)만 DB에서 꺼내와서 다음을 위해 Redis에 채워둔다.

```typescript
async getPost(id: number) {
  const cacheKey = `post:${id}`;

  const cached = await this.redis.get(cacheKey);
  if (cached) {
    return JSON.parse(cached); // 있으면 DB 안 가고 바로 반환 (μs 단위)
  }

  const post = await this.postRepository.findOne({
    where: { id },
    relations: ['category', 'tags', 'blocks'],
  });

  await this.redis.set(cacheKey, JSON.stringify(post), 'EX', 300); // TTL 5분
  return post;
}
```

이 패턴을 Cache-Aside라고 부른다. "먼저 캐시 보고, 없으면 DB 가서 채운다."
여기서 진짜 어려운 건 조회가 아니라 무효화(invalidation)다.
포스트가 수정되면 캐시에 남아 있는 옛날 내용이 문제가 된다.
그래서 수정·삭제 시에는 반드시 관련 캐시를 지워줘야 한다.

```typescript
async updatePost(id: number, dto: UpdatePostDto) {
  const updated = await this.postRepository.save({ id, ...dto });
  await this.redis.del(`post:${id}`); // 낡은 캐시 삭제 → 다음 조회 때 새로 채워짐
  return updated;
}
```

그러니 캐시를 도입한다는 건 CRUD 전반에 관리 포인트가 하나 늘어난다는 뜻이다.
읽기 경로엔 "캐시 먼저, 없으면 DB"가 붙고,
쓰기 경로엔 "이 변경으로 어떤 캐시가 낡았지"를 따지는 무효화가 붙는다.
다만 모든 CRUD에 얹으면 안 된다. 캐시는 공짜가 아니라 무효화 버그와 복잡도를 데려온다.
읽기가 쓰기보다 압도적으로 많고, 계산이 무겁고, 조금 낡아도 괜찮은 데이터에만 선택적으로 씌우는 게 맞다.
잔액이나 재고처럼 매번 최신이어야 하는 값, 유저마다 매번 달라서 캐시 히트가 안 나는 값에는 씌우면 안 된다.

## rate limiting — Redis는 앱 "앞"에 있는 게 아니다

여기서부터 생각이 꼬이기 시작했다.
NestJS 앱은 이미 `@nestjs/throttler`로 rate limiting을 하고 있는데,
Redis로도 rate limiting을 한다는 건 대체 무슨 뜻인가.
Redis가 앱보다 앞단에 있어서 요청을 먼저 거른다는 건가? 그건 아닐 텐데.

아니다. Redis는 백엔드 앞에 서 있는 프록시가 아니다.
요청은 여전히 앱으로 들어오고, 앱이 Redis에게 물어본다.

```
요청 → Nginx → Nest 앱 → (Redis에게 "이 IP 몇 번 왔어?" 질의) → 통과/차단 결정
                  ↓
              PostgreSQL
```

그럼 이미 앱에서 하고 있는데 왜 Redis가 필요한가.
답은 여러 대의 앱 인스턴스가 카운터를 공유해야 하기 때문이다.
`@nestjs/throttler`의 기본 카운터는 그 프로세스의 메모리에 산다. 서버가 한 대면 아무 문제가 없다.
그런데 트래픽이 늘어서 앱 컨테이너를 2대, 3대로 늘리는 순간 문제가 생긴다.
각 인스턴스가 자기가 본 요청만 세기 때문이다.

```
[앱 인스턴스 A] 카운터: 이 IP 50번   ← A는 자기가 본 것만 앎
[앱 인스턴스 B] 카운터: 이 IP 50번   ← B도 자기 것만 앎
로드밸런서가 요청을 반씩 나눠주면
→ 각자 "50번, 아직 100 안 넘음" 판단
→ 실제로는 100번 왔는데 아무도 못 막음
```

Redis에 카운터를 두면 모든 앱이 같은 숫자를 본다.
A로 가든 B로 가든 하나의 카운터를 올리니까 정확히 100번에서 걸린다.
즉 Redis rate limiting이 필요한 건 "앱 이전 단계라서"가 아니라,
인스턴스 간에 상태를 공유하는 단일 진실 공급원(single source of truth)이라서다.

그래서 트레이드오프가 상황에 따라 뒤집힌다.
서버가 한 대뿐이면 인메모리 카운터가 훨씬 낫다.
같은 프로세스의 RAM을 읽으니 네트워크 왕복이 0이라 나노초 단위로 끝난다.
Redis는 아무리 빨라도 네트워크 왕복이 붙는다.

| | 인메모리 throttler | Redis throttler |
|---|---|---|
| 단일 인스턴스 | 빠르고 정확 | 느린데 이득 없음 |
| 다중 인스턴스 | 빠르지만 부정확 | 느려도 정확 |

Redis로 갈아타는 유일한 이유는 인스턴스 여러 개가 카운터를 공유해야 할 때다.
그 순간엔 "약간 느리지만 정확한 Redis"와 "빠르지만 각자 따로 세서 틀리는 인메모리" 중에서 정확성을 위해 속도를 양보하는 것이다.
단일 서버 구조에서 미리 Redis를 붙이는 건 오히려 오버엔지니어링이다.

## 생성이 아니라 접속이다

rate limiting을 이해하고 나니 자연스럽게 다음 의문이 왔다.
앱 인스턴스를 여러 개로 늘리면 Redis 인스턴스도 여러 개가 생기는 것 아닌가?
그러면 카운터가 또 흩어질 텐데, Redis는 어떻게 하나로 유지되는 건가?

여기에 가장 중요한 오해가 있었다.
Redis는 앱 안에 들어 있는 게 아니라, 네트워크 건너편에 따로 떠 있는 별도 서버다.
앱 인스턴스를 늘려도 Redis는 안 늘어난다. 모든 앱이 같은 하나의 Redis에 접속할 뿐이다.

```
[Nest 앱 A] ─┐
[Nest 앱 B] ─┼─→ (네트워크) ─→ [Redis 서버 1대]  ← 모두 여기에 붙음
[Nest 앱 C] ─┘
```

코드로 보면 헷갈림의 원인이 드러난다.
앱마다 이런 코드가 실행되니까 "레디스 인스턴스를 앱마다 만든다"처럼 느껴진다.

```typescript
const redis = new Redis({
  host: 'my-redis.xxxx.cache.amazonaws.com', // 앱 밖에 따로 존재
  port: 6379,
});
```

그런데 이 코드가 만드는 건 Redis 서버가 아니라 클라이언트, 즉 연결이다.
전화기를 드는 것이지 교환국을 짓는 게 아니다.
앱이 3대면 Redis로 향하는 전화선(커넥션)은 3개가 되지만, 받는 교환국(서버)은 여전히 1대다.
`new Redis()`는 생성이 아니라 접속이다.
그 한 대의 교환원이 모든 요청을 순서대로 처리하니까 카운터도 락도 정확히 맞아떨어진다.
이것이 "싱글톤이 유지되는" 원리다.

그리고 이 성질은 Redis만의 것이 아니다.
생각해보면 PostgreSQL도 완전히 똑같다. 오히려 대부분의 백엔드는 이미 이 구조로 돌고 있다.

```typescript
TypeOrmModule.forRoot({
  host: 'xxx.rds.amazonaws.com', // 앱 밖에 따로 존재하는 DB 서버
  port: 5432,
})
```

앱을 여러 대로 늘려도 다 이 한 주소로 붙는다. DB 서버가 앱을 따라 복제되지 않는다.
그러니까 데이터 서버는 "띄우는(생성)" 대상이 아니라 "붙는(접속)" 대상이다.
앱이 늘어날 때 실제로 늘어나는 건 서버가 아니라 그 데이터 서버로 향하는 커넥션 수다.
그래서 앱을 무한정 늘린다고 되는 게 아니라,
결국 뒤에 있는 단일 데이터 서버가 감당하는 총 커넥션과 부하가 진짜 한계가 된다.

이 지점에서 stateless 앱 서버와 stateful 데이터 서버를 분리하는 이유가 한 번에 이해됐다.
앱은 상태를 안 들고 있으니 마음껏 복제·교체·삭제해도 된다. 그래서 스케일아웃이 쉽다.
상태는 전부 뒤의 DB나 Redis에 몰아둔다.
앱은 일하는 일꾼이고 데이터 서버는 창고다. 일꾼을 늘려도 창고는 하나다.

## 그리고 그 크론잡 버그

여기까지 오니 예전에 겪었던 버그가 한 문장으로 꿰어졌다.
회사 프로젝트에서 크론잡이 배포한 앱 개수만큼 여러 번 실행되던 일이 있었다.
당시엔 "왜 앱 수만큼 도는 거지" 하고 의아했는데,
이제 보니 지금까지 이야기한 성질의 직접적인 결과였다.

크론 스케줄러(`@nestjs/schedule` 같은)는 앱 코드 안에 들어 있다.
그런데 앞에서 봤듯 앱 인스턴스는 통째로 복제된다. 스케줄러까지 같이 복제된다.
그러니 각 앱이 자기 시계를 보고 정해진 시각에 각자 독립적으로 작업을 실행한다.

```
새벽 3시 정각
[앱 A] 스케줄러: "실행!" → 정산 배치 돌림
[앱 B] 스케줄러: "실행!" → 정산 배치 또 돌림
[앱 C] 스케줄러: "실행!" → 또 돌림
→ 정산이 3번 실행
```

rate limiting 카운터가 인스턴스마다 따로 놀던 것과 완전히 똑같은 구조의 문제다.
상태 — 여기서는 "이미 실행했는가" — 가 앱 프로세스 안에 갇혀 있어서 인스턴스끼리 서로를 모른다.
정산이나 결제처럼 딱 한 번만 일어나야 하는 작업이 여러 번 실행되면 그대로 사고다.

해결책은 몇 가지가 있다.
하나는 지금까지 이야기한 흐름의 연장선인 분산 락이다.
새벽 3시에 여러 앱이 동시에 깨어나도 딱 하나만 일하게 Redis에 문을 잠근다.

```typescript
@Cron('0 3 * * *')
async runSettlement() {
  // NX = "키 없을 때만 성공" → 동시에 여러 개가 쏴도 딱 1개만 true
  const lock = await this.redis.set('lock:settlement', '1', 'NX', 'EX', 600);
  if (!lock) return; // 나머지는 여기서 조용히 빠짐

  try {
    await this.doSettlement(); // 락을 잡은 1개만 실제로 실행
  } finally {
    await this.redis.del('lock:settlement');
  }
}
```

여러 앱이 동시에 `SET NX`를 쏴도 Redis가 하나씩 처리하니 정확히 한 놈만 락을 잡고 나머지는 빠진다.
`EX 600`은 락을 잡은 앱이 배치 도중에 죽어도 10분 뒤 자동으로 풀리게 하는 안전장치다.
여기서도 Redis가 앱 밖 단일 서버라서, 모든 앱이 같은 락을 보고, 원자적 `NX` 덕에 정확히 하나만 통과한다.
지금까지 이야기한 세 가지가 다 맞물려야 성립한다.

## 결국 어떻게 풀었나

내가 겪은 그 버그는 결국 분산 락이 아니라 다른 방향으로 풀었다.
스케줄러가 도는 인스턴스를 아예 따로 떼어냈다. 크론 전용 `deployment.yaml`을 별도로 만든 것이다.
Kubernetes였기 때문에 구조가 이렇게 나뉘었다.

```yaml
# api-deployment.yaml — 트래픽 받는 앱, 마음껏 스케일아웃
spec:
  replicas: 3          # 여러 개, 스케줄러는 꺼둠
---
# cron-deployment.yaml — 크론 전용
spec:
  replicas: 1          # 딱 1개 → 중복 실행 원천 차단
```

핵심은 `replicas: 1`이다.
"동시에 하나만"을 락으로 사후에 막는 게 아니라, 아예 한 대만 존재하게 해서 문제를 구조적으로 없앤 것이다.
실행 주체가 하나뿐이니 락도 조율도 필요 없다.
트래픽을 받는 API는 3대든 10대든 늘리되 스케줄러는 꺼두고, 크론은 딱 1대에서만 돌게 스케줄러를 켠다.

이 분리가 좋은 이유는 중복 방지만이 아니었다.
API는 트래픽을 따라 스케일아웃해도 크론은 계속 1대라 두 관심사가 완전히 독립적이 된다.
무거운 새벽 배치가 CPU를 다 먹어도 API 응답성에 영향이 없고,
크론 로직만 고쳤을 땐 크론 배포만 다시 하면 되니 API는 무중단으로 유지된다.
실행 주체를 하나로 모으는 것만으로 여러 문제가 한꺼번에 정리됐다.

한 가지 알아둘 미묘한 지점은 있다.
Kubernetes의 `replicas: 1`이 "항상 정확히 1개"를 100% 보장하지는 않는다.
롤링 업데이트나 노드 장애 복구 순간엔 잠깐 옛 파드와 새 파드가 겹쳐서 2개가 될 수 있다.
그 찰나가 크론 시각과 겹치면 이론상 중복이 다시 날 수 있다.
대부분은 확률이 낮아 넘어가지만,
정산처럼 절대 두 번 돌면 안 되는 작업이라면 여기에 분산 락이나 멱등성(두 번 돌아도 결과가 같게) 처리를 한 겹 더 얹는 게 정석이다.
즉 "스케줄러 분리"와 "분산 락"은 배타적인 선택지가 아니라 겹쳐 쌓는 방어선이다.

## 정리

Redis가 무엇인지 알아보려다 도착한 결론은 사실 Redis 자체보다 그 너머에 있었다.
Redis가 다재다능해 보이는 건 새로운 기능을 잔뜩 넣어서가 아니라,
"메모리에서 도는 자료구조"와 "명령이 원자적으로 하나씩 처리됨"이라는 단순한 토대 위에서 캐시·큐·락·카운터가 전부 따라 나오기 때문이다.

그리고 그 토대가 힘을 발휘하는 진짜 이유는, Redis가 앱 밖에 있는 공유된 단일 서버라는 데 있다.
앱은 stateless라서 통째로 복제된다.
그래서 앱 안에 든 모든 것 — 스케줄러, 카운터, 인메모리 캐시 — 도 같이 복제된다.
그러니 인스턴스마다 있으면 안 되는 것, 단 한 번만 일어나야 하는 일은 앱 밖의 공유된 무언가로 끄집어내야 한다.
Redis든, 외부 스케줄러든, DB든.
예전에 겪은 크론잡 중복 실행은 이 원칙을 어겼을 때 어떤 일이 벌어지는지 보여준 사례였고,
크론 전용 배포로 실행 주체를 하나로 모은 건 그 상태를 앱 밖으로 끄집어낸 해결이었다.
그때는 그냥 "이렇게 하니 되네" 하고 넘어갔던 조치가,
Redis를 이해하고 나서야 왜 그게 정답이었는지 뒤늦게 이해됐다.
