MCP라는 말이 나온지도 이제 오래됐다. 2년? 3년?
아무튼 이게 Model Context Protocol의 약자고,
AI가 외부 도구를 쓰게 해주는 무언가라는 것 정도는 알고 있었다.
그리고 별 의문없이 사용하고 있었는데, 사실 이 MCP라는 프로토콜의 존재 의의는 항상 의문이긴 했다.

**AI한테 REST API를 호출하거나 CLI를 호출하는 건 이미 되지 않나?**
클로드 코드는 진작부터 내 셸에서 `gh`도 치고 `psql`도 치고 `curl`로 API도 부른다.
그럼 MCP는 대체 뭘 더 해주길래 따로 프로토콜까지 만들었을까.
이 질문이 실제로 풀린 건 문서를 읽어서가 아니라,
대화 도중에 이상한 걸 목격하고 나서였다.

## 세션 중간에 도구 목록이 업데이트 됐네?
클로드와 다른 주제로 이야기하던 중이었다.
턴이 끝나기도 전에 시스템 메시지가 하나 끼어들었고,
그 순간부터 클로드가 쓸 수 있는 도구가 **32개 늘어나 있었다.**
Figma를 조작하는 도구들이었다.
`get_design_context`, `use_figma`, `generate_diagram` 같은 것들.

더 이상한 건 같은 타이밍에 **두 개가 사라졌다**는 점이다.
`authenticate`와 `complete_authentication`.
인증이 끝나자 서버가 "이제 이 도구는 필요 없다"며 목록에서 빼버린 것이다.

이게 왜 이상한지 감이 잘 안 온다면, 같은 일을 CLI로 상상해보면 된다.
`gh CLI`를 사용하기 위해 로그인은 할 수 있다. 그러나 세션 도중 내 로그인 계정의 권한 변화에 따라 실시간으로 사용할 수 있는 커멘드가 바뀌어봤나?
`git CLI`이 어제는 없던 명령어를 오늘 갑자기 갖고 있던 적이 있나? 없다!
버전 업데이트를 했다거나, 만료되어서 재로그인을 했더니 권한 변경된게 반영된 경우는 있어도, 세션 도중에 바뀌는 일이 없다.

왜냐하면 당연하게도 CLI의 명령어 집합은 **바이너리에 박혀 있고**,
그걸 바꾸려면 바이너리를 새로 깔아야 하기 때문이다.
즉 로컬 프로그램을 새로 깔아야한다는거다.

MCP는 그 전제가 다르다.
이것은 내 로컬에 정본이 있는게 아니라, 서버에서 호출해오는 도구모음인거다. (그게 Figma든 blender든)
그리고 그것이 MCP와 CLI와의 근본적인 차이점이다.

## 결정적 차이는 "누가 도구의 존재를 알고 사용할 것인가"
MCP는 Anthropic이 2024년 11월에 공개한 오픈 프로토콜이다.
지금은 OpenAI, Google, Microsoft도 다 채택했다.

실체는 거창하지 않다.
**JSON-RPC 2.0(RPC의 정의 스펙) 위에 추가로 얹은 규약**이다.

여기서 많이들 하는 흔한 오해가 있는데,
MCP는 CLI나 API로 못 하던 걸 가능하게 만드는 물건이 아니다.

CLI로 되는 건 MCP로도 되고, 대체로 그 반대도 된다. 능력의 차이가 아니다.
진짜 차이는 **AI가 언제 그 도구의 존재와 사용법을 알게 되는가?**에 달려있다.

CLI나 API를 쓰려면 **모델이 이 CLI의 사용법을 미리 알고 있어야 한다.**
`gh pr list --json number,title`을 치려면 그 명령이 존재하고,
`--json` 플래그가 있고,
어떤 필드명을 받는지를 사전 지식으로 갖고 있거나 `--help`를 파싱해서 알아내야 한다.
학습 데이터에 없는 사내 CLI라면 매번 문서를 읽혀야 한다.

MCP는 접속하는 순간 **서버가 자기 도구 목록을 스스로 카탈로그로 보여준다.**
이름, 설명, 그리고 파라미터의 JSON Schema까지 통째로.

앞서 말한 피그마 MCP의 경우에도,
모델이 Figma에 대해 아무것도 몰랐다 해도
서버가 붙는 순간부터 `get_design_context`가 어떤 인자를 받는지 정확히 알게 되는 것이다.

## 그럼 REST API를 직접 부르는 것과는 뭐가 다른가

REST가 표준화한 건 "네트워크 너머의 컴퓨터에게 어떻게 자원을 달라고 요청하는가"다.
자원을 URL로 식별하고, 동사는 HTTP 메서드로, 표현은 JSON으로.
이 프로토콜은 아주 잘 작동해왔고 지금도 잘 작동한다.

REST가 표준화하지 않은 건 다른 질문이다.
**호출하는 쪽이 사람이 아니라 AI 모델일 때,**
**이 API에 뭐가 있고 언제 어떻게 써야 하는지를 어떻게 알아내는가.**

지금까지 그 공백은 사람이 메웠다.
문서를 읽고, 인증을 붙이고, 스키마를 맞춰서 글루 코드를 쓰는 식으로.
API마다 페이지네이션 방식이 다르고 에러 형식이 다르고 인증이 다른데,
그 차이를 흡수하는 건 언제나 개발자의 손이었다.

MCP는 그 사람의 일을 프로토콜로 옮긴 것이다.
구체적으로 REST에 없어서 새로 만든 것들을 보면 이렇다.
첫째, **모델용 자기 서술**이다.
MCP 서버는 `tools/list` 요청 하나로
"이런 도구가 있고, 입력 스키마는 이거고, 이럴 때 써라"를
모델이 바로 소비할 수 있는 형태로 돌려준다.

REST에는 이 표준이 없다.
OpenAPI가 있지 않냐고 할 수 있는데,
OpenAPI는 선택 사항이고, 사람 독자를 위해 쓰여 있고, 통째로 프롬프트에 넣기엔 너무 크다.
ChatGPT 플러그인이 정확히 "OpenAPI 스펙을 모델에 주자"는 시도였고, 그래서 잘 안 됐다.
설명이 모델을 위해 쓰이지 않았고, 스펙 전체가 컨텍스트를 잡아먹었다.

물론 REST API로 MCP와 동일한 구조를 만든다면 별 차이는 없을거다.
그러나 REST API의 자유로운 형식과 구분지어 MCP라는 이 새로운 구조를 만들 필요성이 생긴 것이다.


둘째, **N×M 문제**다.
표준이 없으면 어떻게 되는지부터 보자.
AI 호스트(Claude Code, Cursor, ChatGPT, VS Code Copilot)가 각자 자기만의 플러그인 형식을 가진다고 하자.

GitHub이 이 넷에 붙고 싶으면
Claude용, Cursor용, ChatGPT용, Copilot용 플러그인을 따로 네 개 만들어야 한다.
Slack도 네 개, Postgres도 네 개... 이렇게 AI 에이전트 서비스마다 각 서비스들이 플러그인을 따로따로 낸다면
벌서 호스트 4개에 서비스 10개면 통합 코드가 40벌이다.

표준이 있으면 규약을 하나 정하고 양쪽이 각각 그 규약만 구현한다.
호스트는 "MCP 클라이언트"를 한 번 구현하고, 서비스는 "MCP 서버"를 한 번 구현한다.
4 + 10 = 14벌이면 끝이고, 조합은 전부 자동으로 성립한다.
새 호스트가 나오면 그 호스트가 클라이언트 하나만 구현하면 기존 서버 10개가 그냥 붙는다.
서비스 쪽은 아무것도 안 해도 된다.
이것이 표준화된 규격의 힘이다.


셋째, **로컬 프로세스 전송**이다.
REST는 네트워크 서비스용이다.
파일시스템, git, 브라우저처럼 내 머신 안의 것에 접근하려고 HTTP 서버를 띄우는 건 어색하다.
MCP는 stdio 전송을 표준으로 넣어서 로컬 프로세스도 같은 방식으로 붙게 했다.
이 부분은 뒤에서 따로 다룬다.

넷째, **양방향·상태 있는 세션**이다.
REST는 요청·응답 한 방향이다.
MCP는 서버가 "도구 목록이 바뀌었다"고 알리거나, 진행률을 보내거나,
서버 쪽에서 거꾸로 클라이언트의 모델에게 생성을 요청하거나(sampling),
사용자에게 되묻는(elicitation) 것까지 규정한다.

다섯째, 도구 외의 **원시 타입**이다.
tools 말고도 resources(모델이 읽을 컨텍스트)와 prompts(재사용 템플릿)를 따로 구분한다.
REST엔 그런 구분 자체가 없다.
비유하자면 REST는 전기이고 MCP는 USB-C 규격이다.
전기로 뭐든 할 수 있지만,
기기마다 다른 플러그를 매번 사람이 납땜하던 걸 없앤 것이다.

## stdio로 네트워크 너머와 통신할 수 있나
앞서 장점들을 훑어보던 중 **로컬 프로세스 전송** 부분이 약간 이해하기 힘들었다.
MCP가 stdio 전송을 표준으로 넣었다는데, stdio는 내 컴퓨터 안에서 쓰는 것 아닌가.
그걸로 어떻게 네트워크 너머의 컴퓨터와 통신한다는 건가.

결론은 못 한다. stdio 자체로는 네트워크를 건너지 못한다.
stdio는 로컬 전용이고, 원격은 MCP의 다른 전송 방식이 맡는다.

용어부터 정리하면 stdio는 프로세스마다 붙어 있는 세 개의 파일 디스크립터다.
표준 입력(0), 표준 출력(1), 표준 오류(2).
부모 프로세스가 자식을 띄울 때 이 파이프를 연결하면,
부모는 자식의 stdin에 쓰고 stdout에서 읽는 식으로 대화할 수 있다.
셸에서 `cat file | grep foo`가 동작하는 원리와 같다.

MCP의 stdio 전송은 정확히 이걸 쓴다.
호스트(Claude Code 같은 클라이언트)가 MCP 서버를 **자식 프로세스로 직접 실행**하고,
stdin으로 JSON-RPC 요청을 한 줄씩 밀어 넣고 stdout으로 응답을 받는다.

그래서 서버는 반드시 호스트와 같은 머신에 있어야 한다.
대신 장점이 뚜렷하다. 포트를 열 필요가 없고, 인증이 필요 없고(호스트가 직접 띄웠으니 그 자체가 신뢰),
프로세스가 죽으면 파이프도 끊겨서 수명 관리가 간단하다.
파일시스템이나 git처럼 내 머신 안의 것을 다루는 서버에 딱 맞는다.

네트워크 너머의 서버는 두 번째 전송 방식이 맡는다.
현재 표준은 **Streamable HTTP**다.
클라이언트가 서버의 단일 엔드포인트로 HTTP POST를 보내고,
서버가 알림을 밀어야 할 땐 SSE(Server-Sent Events) 스트림을 연다.
OAuth 같은 인증이 여기 붙는다.

```typescript
Claude Code  <-- stdio (JSON-RPC, MCP 규격) -->  MCP 서버 프로세스  --> 뭐든 (REST, gRPC, DB 드라이버, 파일시스템, 브라우저 확장...)
```

구조를 정리하자면 위 표와 같다. 클로드 코드가 자식 프로세스로 MCP 서버를 띄우고, stdio방식으로 소통한다.
MCP서버 자체는 외부 네트워크와 Streamable HTTP(현재표준)든 REST든 뭐든... 소통하는 것이다.
(초기 스펙에서 쓰던 HTTP+SSE 방식은 두 엔드포인트 구조였는데 지금은 폐기 예정이다.)

"원격 MCP 서버"라고 부르는 것들은 전부 이 방식이다.
즉 MCP는 메시지 형식은 JSON-RPC로 고정하고,
그걸 실어 나르는 배관은 로컬이면 stdio, 원격이면 HTTP로 나눠 놓은 것이다.
서버 코드 입장에선 위쪽 로직이 같고 전송 계층만 갈아 끼운다.

## MCP는 일회성 호출이 아니라 유지되는 세션이다
세 번째 의문은 이거였다. 그러면 MCP를 쓴다는 건 REST처럼 필요할 때 한 번 호출하고 끝나는 게 아니라,
Claude Code가 MCP 서버를 어딘가 포트에 띄워 두는 건가.

MCP는 일회성 호출이 아니라 **세션 연결**이다. 소켓 연결과 비슷하다고 봐야되나...
하지만 "포트에 띄운다"는 건 서버 종류에 따라 다르고,
로컬 서버는 포트를 아예 쓰지 않는다.

세션이라는 점부터 보자.
MCP 연결은 요청 하나 보내고 끝이 아니다.
세션을 열 때 초기화 핸드셰이크를 한다.

클라이언트가 자기 프로토콜 버전과 능력을 보내고, 서버가 자기 능력을 돌려주고,
그다음 도구 목록을 받아 온다.
이후 도구 호출은 전부 그 세션 위에서 오간다.

서버는 세션 중간에 "도구 목록 바뀜" 같은 알림을 밀 수도 있다.
Claude Code가 세션을 시작할 때 MCP 서버들에 붙고, 세션을 닫으면 끊는다.

포트를 띄우는지는 전송 방식에 따라 갈린다.
stdio 서버라면 Claude Code가 서버를 자식 프로세스로 직접 실행한다.
포트가 없다. 파이프로만 대화한다.

실제로 내 맥북에서 프로세스 목록을 뽑아 보면 이렇게 보인다.
회사 플러그인의 MCP 프록시가 Claude Code 세션마다 하나씩 자식 프로세스로 떠 있다.

```bash
$ ps aux | grep mcp
beomhwan  77949  ...  s001  node .../***/scripts/***-mcp-proxy.mjs
beomhwan  23494  ...  s000  node .../***/scripts/***-mcp-proxy.mjs
beomhwan  11812  ...  s007  node .../***/scripts/***-mcp-proxy.mjs
beomhwan  92464  ...  s003  node .../***/scripts/***-mcp-proxy.mjs
beomhwan  10359  ...  s006  node .../***/scripts/***-mcp-proxy.mjs
```

터미널 세션이 5개 열려 있어서 5개가 떠 있고, 각 세션이 닫히면 같이 죽는다.
어느 것도 포트를 열지 않았다.

HTTP 서버라면 반대로 Claude Code는 아무것도 띄우지 않는다.
남이 이미 운영 중인 서버에 클라이언트로 접속한다.
같은 머신의 설정을 보면 Figma가 그렇게 잡혀 있다.

```bash
$ claude mcp list
plugin:figma:figma: https://mcp.figma.com/mcp (HTTP) - ! Needs authentication
```

이 경우 세션은 HTTP 헤더의 세션 ID로 유지된다.
요청마다 새 TCP 연결을 맺더라도 서버 쪽에선 "아까 그 클라이언트"로 이어 본다.
즉 REST와 같은 배관을 쓰지만, 의미상으론 상태 있는 세션이다.

정리하면 포트를 여는 주체는 Claude Code가 아니라 원격 MCP 서버의 운영자이고,
Claude Code는 로컬 서버라면 프로세스를 띄우고 원격 서버라면 접속만 한다.
둘 다 공통으로 "세션을 열어 두고 그 안에서 여러 번 도구를 부른다"는 점이
REST 호출과 다르다.

---

## 그러나 단점도 있다. 도구 정의는 컨텍스트를 꽤 먹는다
글 초반에 예시로 든 Figma MCP의 경우로 돌아가보자.
도구 하나의 정의는 이름 한 줄이 아니라 설명문과 파라미터 JSON Schema 전부다.
Figma의 `use_figma` 같은 도구는 설명만으로도 수백 토큰이다.
32개를 통째로 상시 로드하면 **대화를 시작하기도 전에 컨텍스트 수천 토큰이 영구 점유된다.**
서버를 대여섯 개 붙이면 그것만으로 컨텍스트의 상당 부분이 날아간다.
그래서 클로드 코드는 도구를 지연(deferred) 상태로 두고,
이름만 보여준 뒤 실제로 쓸 때 스키마를 당겨오는 방식을 쓴다.

이건 MCP의 편의성이 공짜가 아니라는 걸 클라이언트 쪽에서 인정하고 만든 우회로다.
**도구를 많이 붙일수록 모델이 멍청해질 수 있다**는 게 이 프로토콜의 가장 현실적인 제약이다.

솔직히 비판도 맞는 부분이 있다.
도구 정의가 컨텍스트 토큰을 먹고, 보안 모델은 아직 허술하고,
프로토콜 스펙이 아직도 자주 바뀐다.

그래도 필요한 이유는 하나로 요약된다.
호출자가 사람에서 모델로 바뀌면서 필요해진 건 새로운 전송 방식이 아니라
**새로운 발견·서술 규약**이었고, REST는 그걸 애초에 다루지 않는다.

MCP는 그 빈칸을 채우려고 만든 것이고, 그 아래 배관은 원래 있던 걸 그대로 쓴다.
"다 REST로 되지 않나"라는 말은 반쯤 맞다.
배관은 REST로 된다.
발견은 안 된다.
