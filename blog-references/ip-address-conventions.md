감사 로그를 보다 보면 IP가 잔뜩 찍힌다.
`210.90.x.x`, `172.17.0.3`, `54.180.x.x` 같은 것들.
이걸 보자마자 "아 이건 한국 통신사, 이건 Docker 컨테이너, 이건 AWS 서버"라고
감이 오는 사람과 매번 검색하는 사람의 차이는 '컨벤션을 아는가?'이다.

IP 주소 자체엔 아무 의미가 없지만, 주소가 배정된 역사와 예약 규칙이 있어서 첫 몇 자리만 봐도 꽤 많은 걸 추정할 수 있다.
그 컨벤션들을 정리했다.

먼저 자주 나오는 질문 하나. 220으로 시작하면 한국인가?
"아시아태평양일 확률이 높다" 정도이지 한국 확정은 아니다.
218부터 223까지의 블록이 2000년대 초 아시아태평양 배정 기관(APNIC)에 통째로 배정돼서 한국, 일본, 중국, 호주가 나눠 썼다.

한국 통신사 블록이 꽤 많이 들어 있긴 하다.
첫 옥텟만 보고 나라를 맞히는 건 확률 게임이고, 확실히 알려면 `whois` 한 줄이면 된다.

## 보자마자 "이건 인터넷 주소가 아니다"라고 알아채는 것들
제일 자주 써먹는 축이다.
아래 범위는 인터넷에서 라우팅되지 않거나 특수 용도로 예약돼 있어서(사설 IP),
로그에 보이면 "공인 인터넷에서 온게 아니다"라고 바로 알 수 있다.

*「사설」은 **「인터넷에서 통용되지 않는, 집안용」** 영어 private의 번역인데, 사적 소유가 아니라 「비공개 구역」 쪽 의미다. 반대말은 공인IP.

| 범위 | 정체 | 한마디 |
|---|---|---|
| `10.x.x.x` | 사설 | 회사망, AWS VPC 기본값 |
| `172.16~31.x.x` | 사설 | Docker 컨테이너가 보통 `172.17.0.x` |
| `192.168.x.x` | 사설 | 집 공유기. `192.168.0.1`이나 `.1.1`이 공유기 자신 |
| `127.0.0.1` | 사설 | 루프백. 서버 자기 자신 (localhost) |
| `127.x.x.x` | 루프백 | `127.0.0.1` = localhost, 자기 자신 |
| `0.0.0.0` | "모든 인터페이스" | 바인딩 주소로 쓰면 노출, 목적지로는 무의미 |
| `169.254.x.x` | 링크 로컬 | DHCP 실패 시 자동 배정. 이게 뜨면 "공유기와 연결이 안 됐다" |
| `169.254.169.254` | 클라우드 메타데이터 | EC2 안에서 이 주소를 curl하면 인스턴스 정보와 IAM 자격증명이 나온다. SSRF 공격의 단골 목표 |
| `100.64~127.x.x` | CGNAT 공유 대역 | 통신사 NAT 안쪽. Tailscale이 이 대역을 빌려 쓴다 |
| `224~239.x.x.x` | 멀티캐스트 | 일반 트래픽에선 안 보임 |
| `240~255.x.x.x` | 예약 | `255.255.255.255`는 브로드캐스트 |
| `192.0.2.x`, `198.51.100.x`, `203.0.113.x` | 문서용 | 예시 코드나 RFC에서 "가짜 주소"로 쓰는 것. 실제로 안 쓰임 |
사설 대역 셋은 특히 중요하다.
이 주소들은 전 세계 어디서나 중복해서 쓸 수 있고, 인터넷에선 아무 데도 못 가기 때문에 충돌이 안 난다.
그래서 서버 로그에 `192.168.x.x`가 찍혀 있다면 요청이 바깥에서 온 게 아니라 같은 네트워크 안, 혹은 프록시 뒤에서 온 것이다.

리버스 프록시를 세워 두고 실제 클라이언트 IP 대신 프록시의 사설 IP만 찍히는 사고가 정확히 이 모양이다.
`169.254.169.254`는 따로 외워 둘 가치가 있다.
EC2 안에서 이 주소로 HTTP 요청을 보내면 인스턴스에 붙은 IAM 역할의 임시 자격증명이 나온다.
그래서 서버가 사용자 입력 URL을 대신 fetch해 주는 기능이 있으면, 공격자가 이 주소를 넣어서 자격증명을 빼 가는 SSRF 공격이 가능하다.
URL을 대신 가져오는 기능을 만들 땐 이 주소와 사설 대역을 막는 게 기본이다.

## 외워 두면 아는 체가 되는 공인 주소들
| 주소 | 정체 |
|---|---|
| `8.8.8.8` | Google DNS. "인터넷 되나?" 확인용 ping의 표준 |
| `1.1.1.1` | Cloudflare DNS |
| `9.9.9.9` | Quad9 DNS |
| `168.126.63.1` | KT DNS. 한국 개발자의 고전. 옛날 PC방 세팅할 때 외우던 그 주소 |
| `210.220.163.82` | SK브로드밴드 DNS |
| `164.124.101.2` | LG유플러스 DNS |
`ping 8.8.8.8`은 되는데 `ping google.com`이 안 되면 인터넷은 붙었고 DNS만 죽은 것이다.
이 한 줄 진단이 네트워크 문제의 절반을 가른다.


## 첫 옥텟으로 클라우드를 알아보는 것
로그에 찍힌 IP가 어느 회사 서버인지 대충 감 잡을 때 쓴다.
정확하진 않고 대표적인 것만이다.
| 첫 옥텟 | 대체로 |
|---|---|
| 3, 13, 18, 52, 54 | AWS |
| 34, 35 | Google Cloud |
| 20, 40 | Azure |
| 104.16~31, 172.64~71 | Cloudflare (사이트가 Cloudflare 뒤에 있으면 이게 보인다) |
이 축이 유용한 이유는 "사람인가 봇인가"를 가르는 첫 번째 필터가 되기 때문이다.
일반 사용자는 통신사 IP에서 오고, 크롤러와 봇은 클라우드 IP에서 온다.
예전에 크롤러 공격을 정리할 때 봤던 IP들도 대부분 이 축에 있었다.


## 한국 통신사가 많이 갖고 있는 첫 옥텟
확정이 아니라 "한국일 가능성이 높다"는 감이다.
통신사가 블록을 재배정하기도 하니 참고용으로만.

- KT는 `1.x`의 상당 부분, `14.x`, `39.x`, `49.x`, `118.x`, `175.x`, `211.x`, `218~222.x`에 큰 블록이 있다.
- SK브로드밴드는 `58.x`, `59.x`, `121.x`, `125.x`, `175.x`, `211.x`, `220.x`, `222.x`.
- LG유플러스는 `1.x`, `27.x`, `61.x`, `106.x`, `114.x`, `211.x`, `218.x`.
- 대학은 클래식한 것들이 있다. KAIST `143.248.x.x`, 서울대 `147.46.x.x`, 연구망 KREONET `128.134.x.x`.

정리하면 `1`, `14`, `27`, `39`, `49`, `58`, `59`, `61`, `106`, `110~125`, `175`, `180~183`, `203`, `210`, `211`, `218~223`은 APNIC 색이 짙고 그중 한국 비중이 크다.
반대로 `3`, `13`, `18`, `34`, `35`, `52`, `54`가 보이면 사람이 아니라 클라우드 서버, 즉 봇이나 크롤러일 확률이 높다.


## 표기 컨벤션
`/24` 같은 슬래시는 "앞 24비트가 네트워크"라는 뜻이다.
`/8`은 첫 옥텟 하나가 고정(약 1,600만 개), `/16`은 두 개 고정(약 6만 5천 개), `/24`는 세 개 고정(256개), `/32`는 주소 하나다.
보안그룹에서 "내 IP만 허용"이 `/32`인 이유다.
옛날엔 클래스 A/B/C라고 불렀는데 지금은 안 쓰고,
그래도 "클래스 C 하나"라고 하면 `/24`를 뜻하는 관용어로 남아 있다.


## 포트 쪽 컨벤션도 세트로
포트 번호에도 같은 종류의 관습이 있다.
0~1023은 잘 알려진 포트라서 root 권한이 있어야 열 수 있다.
개발 서버가 3000, 8080처럼 1024 위에 뜨는 이유다.
49152~65535는 클라이언트가 나갈 때 임시로 쓰는 범위라서,
NAT 변환 테이블에 보이는 `51234` 같은 출발지 포트가 여기서 나온다.

자주 보는 것은 22 SSH, 53 DNS, 80 HTTP, 443 HTTPS, 3306 MySQL, 5432 Postgres, 6379 Redis, 27017 MongoDB다.
이 블로그가 프론트, 백엔드 포트는 4000번대로 쓰는 건 이 어느 것과도 안 겹치게 고른 것이다.


## 확인하는 법
아는 체하다가 틀리면 곤란하니 도구도 같이 알아 두면 된다.

```bash
whois 220.90.1.1            # 배정 기관과 소유 통신사
curl ipinfo.io/220.90.1.1   # 상용 DB 기준 국가·도시 추정
dig -x 220.90.1.1           # 역DNS. 통신사 이름이 호스트명에 박혀 있기도 하다
curl ifconfig.me            # 지금 내 공인 IP (NAT 바깥에서 보이는 주소)
```

첫 옥텟으로 감을 잡고, 확신이 필요하면 `whois`로 확인한다.
그 순서만 지키면 아는 체는 충분히 된다.
